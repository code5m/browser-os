# Rebased / IntelliJ Git Studio 产品设计

## 调研结论

Rebased 是以 IntelliJ 平台为基础的 Git 客户端，不是独立的 Git 交互模型。其核心取舍是把 Git Log 当作主工作区，并允许用户在设置中把日志切回传统的底部工具窗口。BrowserOS 采用同一条工作流，但不复制 Rebased 的视觉资产、品牌或源码。

研究来源：

- [Rebased 项目说明](https://github.com/DetachHead/rebased)：其保留 IntelliJ Git 集成，并明确提供“Git Log 位于编辑器或底部工具窗口”的布局选择。
- [Rebased 最新发布页](https://github.com/DetachHead/rebased/releases)：用于确认当前发布线和产品仍在持续维护。
- [IntelliJ Git 合并、变基与挑选提交流程](https://www.jetbrains.com/help/idea/apply-changes-from-one-branch-to-another.html)：提交详情先确认、Cherry-pick 失败进入冲突处理、可针对单文件操作。

## BrowserOS 采用的完整交互模型

### 常规历史审查

```text
┌──────────────────┬──────────┬──────────────────────────────────────────────┐
│ 提交详情与文件    │  ↔ 拖动  │ 文件编辑 / 预览区                            │
│                  │          │                                              │
│ SHA、作者、时间   │          │ [文件编辑器] [并排 Diff] [统一 Patch]         │
│ 变更文件、筛选    │          │ [仅变更区域 / 全部内容] [折叠 / 展开]          │
│ 上一个/下一个文件 │          │                                              │
├───────────────────────────────────────────────────────────────────────────┤
│                                ↕ 拖动                                      │
├──────────────────┬────────────────────────────────────────────────────────┤
│ 分支             │ 提交图与历史                                            │
│ 本地 / 远程      │ 搜索、作者过滤、分页、提交标签、Cherry-pick             │
│ 比较 / 合并操作  │ 选中提交后自动载入第一个变更文件                        │
└──────────────────┴────────────────────────────────────────────────────────┘
```

1. 用户在底部历史选择提交；首个变更文件自动打开，减少“选中了但没有内容”的空状态。
2. 左侧固定展示当前提交的文件树和元信息；文件可筛选、逐个切换、前后跳转，并支持与当前工作区只读比较。
3. 中央是唯一的审查面：文件全文、并排 Diff、统一 Patch 三种模式互斥；全文模式展示历史 blob，Diff 模式展示该次提交相对父提交的变化。
4. “只显示变更区域”在 Diff 模式下隐藏上下文行；“显示全部内容”恢复完整上下文。编辑器区可折叠以专注提交图。
5. 右/下拖动条由 Pointer 事件控制，有 260–520 px 的详情宽度、180–620 px 的底部高度边界，避免布局缩成不可用区域。
6. 删除文件仍是有效提交项：全文模式提示该版本不存在，Diff 模式仍显示删除内容，不再因为读取历史 blob 失败而丢掉选中状态。

### 工作区改动

- 三个文件组：冲突、Index、Working Tree；同一文件的已暂存与未暂存状态分别可查看。
- 审查支持并排、补丁、三版本全文、按 hunk/行暂存、Blame、跟随重命名历史。
- 所有写入保持 BrowserOS 的双阶段“预览 → 用户确认 → 执行”机制；不借鉴 IDE 的单击直接写入行为。

### 冲突、Merge、Rebase、Cherry-pick

```text
┌─────────────────┬─────────────────────────────┬─────────────────┐
│ 当前版本 ours    │ 冲突编辑区                   │ 目标版本 theirs  │
│                 │ [采用当前] [采用目标]         │                 │
│ 只读文本         │ 可手动编辑最终结果            │ 只读文本         │
└─────────────────┴─────────────────────────────┴─────────────────┘
```

- 左、中、右分别保持当前版本、最终结果、目标版本；不把三方内容混进普通编辑器。
- 两个“采用”按钮是明确整块替换，不会静默写盘；最终仍进入预览确认。
- Merge / Rebase / Cherry-pick 未完成时，页面只提供继续或中止动作，禁止部分提交。

## 已实现边界

- 正常模式按上述三段式布局，不再把分支、提交、提交详情和 Diff 竞争同一行空间。
- 变更文件在左、文件预览在中央、分支和历史在下；两个分割条都可拖动。
- 删除文件、二进制文件和超大文件有可解释的中央状态，不会阻断 Diff 阅读。
- Git 读取继续限制在已授权仓库；Git 写入、远端操作和冲突保存继续受预览确认、状态快照和能力生命周期约束。

## 不在本次范围

- IntelliJ 的语言级代码分析、完整 Changelist、交互式 rebase 队列、代码编辑并保存到工作区。
- 这些需要新的产品授权或更大范围的原生/文件编辑能力，不能把“查看历史”误扩张为“任意修改 Git 历史”。

## 按钮与操作分层审查（2026-10-20）

本次按 Rebased 1.1.22 发布说明、公开 README 与 IntelliJ Git 工作流复核了原型的操作层级。结论是：Git Log 应作为主审查对象，但提交操作必须跟随当前选择的提交、文件或分支出现，不能把所有危险操作长期平铺在全局栏。

| 操作层级 | 原型按钮 | 交互约束 |
|---|---|---|
| 全局仓库 | 刷新、获取更新、推送、更多 | 显示 ahead/behind；推送只进入预览，不直接执行 |
| 页面导航 | 改动、提交历史、暂存架、工作树、PR/CI | 切换页面不丢失当前选中提交和编辑视图 |
| 提交上下文 | 与本地比较、复制路径、挑选提交、撤销提交、更多 | 必须先选中提交；高风险动作显示影响文件和确认步骤 |
| 历史筛选 | 说明/作者/Hash、检索、筛选 | 筛选只改变列表，不改变工作树 |
| 分支上下文 | 与 HEAD 比较、切换、合并、变基 | 必须选中目标分支；Merge/Rebase 进入预览与冲突状态 |
| 编辑器 | 折叠、只看变更、文件/Diff/Patch | 三种视图互斥；折叠不改变选中状态 |
| 冲突块级 | 接受当前块、接受目标块、采用当前、采用目标 | 左右只读，中间可编辑；每次接受都可继续撤销或中止 |

本次审查还补齐了原型中之前缺失的三个行为：历史检索会真实过滤提交；分支点击会反馈当前选择；顶部与提交级按钮都会进入状态栏提示而不是伪装成已经执行 Git 写操作。原型仍不宣称真实 Git 写入已完成，真实命令必须由 GitStudio 运行时的预览确认链承接。
