# BrowserOS MCP effect status inbox v1

## Trust and scope

Opt in only for an independently verified provider which implements durable idempotency and immutable finality for the exact effect. Ordinary MCP tools, tool annotations, transport return, timeout, process termination, "not found", and untrusted structured content are not provider authority. Do not pin a key generated by a workspace or by an unreviewed server. No private signing key is given to the MCP child. No network access or remote polling process is added.

Native user configuration: `<BrowserOS data dir>/coding-mcp.json`. Add to the chosen existing stdio server's object:

```json
{
  "browseros_effect_authority": {
    "version": 1,
    "account": "provider-account-id",
    "namespace": "provider-operation-namespace",
    "public_key": "REPLACE_WITH_CANONICAL_BASE64_ED25519_PUBLIC_KEY"
  }
}
```

The public key is standard padded base64 of exactly 32 bytes. Account and namespace are 1–128 ASCII alphanumeric, dot, underscore, colon or hyphen characters. The user's approval view shows the authority and inbox and binds the entire reviewed configuration. Generic MCP behavior is unchanged when absent.

## Dispatch and publication

For a reviewed `tools/call` the native owner supplies `params._meta["browseros/effect/v1"]`:

```json
{
  "version": 1,
  "run_id": "<original Run UUID>",
  "idempotency_key": "browseros:<native effect UUID>",
  "review_revision": "<64 lowercase hex digits>",
  "account": "<pinned account>",
  "namespace": "<pinned namespace>"
}
```

The provider must bind its actual business operation to that unique key before performing any effect, reject duplicate or mismatched keys, and guarantee a terminal outcome cannot change or be followed by another effect for the same key. An independent trusted provider or relay writes `<data dir>/mcp-effect-status/<native effect UUID>.json` via an atomic same-directory replacement, max 4096 bytes. This is a pull-on-read inbox; a remote provider integration must deliver the signed file. The original MCP executable is never restarted to query status.

The signed JSON has exactly these fields:

```json
{
  "version": 1,
  "run_id": "<original Run UUID>",
  "idempotency_key": "browseros:<native effect UUID>",
  "review_revision": "<original 64-character digest>",
  "account": "<original pinned account>",
  "namespace": "<original pinned namespace>",
  "outcome": "applied_final",
  "signature": "<canonical standard base64 Ed25519 signature (64 bytes)>"
}
```

Only `applied_final` and `not_applied_final` are accepted. Do not sign not-applied for an absent key, a pending operation, a timeout or eventual-consistency gap. Sign the UTF-8 bytes of these eight ASCII lines joined by LF, with no trailing newline:

```text
browseros.mcp.effect.final.v1
1
<run_id>
<idempotency_key>
<review_revision>
<account>
<namespace>
<outcome>
```

## Native settlement

Manual MCP checks the signed inbox after the original local return and whenever the history or exact receipt is queried. An opted-in effect is unknown until a verified final status arrives. The original Run is permanently non-replayable.

Coding MCP checks after original native return and when the same session is read; the encrypted session/workspace owner updates only the original unknown operation. The model receives a fixed native-generated status notice, not publisher content. The user may explicitly resume the model; no original approval is replayed.

The provider proof is retained in the authenticated encrypted record. Human attestation remains distinguishable. Final status does not prove that a local process or unrelated side effect ended; process cleanup and recovery remain separate. A malformed or absent file never closes uncertainty. Do not sign contradictory final statuses. Remove consumed files only after observing the persisted terminal receipt.

## Verification boundary

Native consumer source and signature fixtures are implemented. Real provider/relay configuration, provider-side idempotency, signing key provenance, end-to-end platform execution and fault injection require verification separately. No real provider deployment or integration test is claimed. No new dependency, IPC command, automatic remote polling, or workflow change is required.
