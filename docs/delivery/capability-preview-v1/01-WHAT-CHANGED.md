# 01 — 为什么要做模块化？现在比之前好在哪？

## 一、为什么要做

这个项目已经积累了 18 个功能域（浏览器、多窗口宫格、文件工作区、终端、书签、凭据、数据库、
Git、AI Agent、技能、插件、知识图谱、笔记、采集、任务、会话、脚本、工作台）。

功能越多，三个问题越明显：

1. **边界靠人记**：新增一个功能，它该依赖谁、能不能关、会不会影响别的——没有地方写清楚。
2. **AI 协作容易"再造一个"**：同一个状态被多处读写、同一个动作出现多个入口。
   （这个问题上一阶段已用 **Semantic Registry（语义登记表）** 解决。）
3. **资源与启停没说法**：想关掉某个功能省资源，没人能回答"关了到底能省什么、会不会连带出问题"。

本次做的，就是在**语义治理已冻结的基础上**，再加一层 **Capability（能力）体系**。

---

## 二、两套登记表的分工（不重复、不冲突）

| 问题 | 谁回答 |
|---|---|
| 这个状态/动作**是什么意思**、谁拥有、谁能改 | **Semantic Registry**（上一阶段已冻结，本次未改） |
| 这个能力**提供什么、依赖什么**、生命周期与资源策略 | **Capability Registry**（本次新增） |

> 两套表**不重复维护同一个事实**：能力表只"引用"语义表里的归属，不重新定义语义。
> 有机器校验（checker）强制这一点——违反就拦下。

---

## 三、现在比之前好在哪（可验证，不是口号）

| 能力 | 之前 | 现在 |
|---|---|---|
| 功能边界 | 口头/代码里 | 18 个能力的 **manifest 清单**（id/提供/依赖/生命周期/资源/权限/持久化） |
| 依赖关系 | 靠读代码 | `dependencies.yaml` **显式登记 + 机器检测循环依赖/禁止方向** |
| 谁能关 | 不知道 | 每个能力声明 `suspendable / destroyable / resident` |
| 资源开销 | 凭感觉 | 13 类资源分类 + 每能力的资源策略（声明式） |
| 改动安全 | 人工检查 | 3 个 checker + 行为门禁，合计 **44 条断言全绿** |
| 出错恢复 | 靠运气 | 每个阶段一个 **annotated tag**，共 6 个恢复点 |

**断言统计（本次新增）**

```text
check-capability-registry.mjs    自检 13/13 · 真实扫描 fail=0 warn=0 · --strict 亦通过
check-capability-runtime.mjs     RT-01..RT-15        15/15 PASS
check-capability-pilot.mjs       PLT-01..PLT-08       8/8 PASS
capability-resource-report.mjs   RPT-01..RPT-08       8/8 PASS
既有语义治理（回归验证）          Registry ALL_PASS / Closure 27/27 / Sensitive ALL_PASS / 真实扫描 fail=0
```

---

## 四、这次**没有**做的事（避免过度承诺）

- 没有把项目拆成几十个 npm 包
- 没有移动任何既有业务代码目录
- 没有删除旧系统（新能力是"包"在旧系统外面的兼容层）
- 没有改动您当前已安装的程序

一句话：**这次是"先把账理清、把规矩立起来"，不是"推倒重来"。**
