# 05 — 稳定性与恢复：一个能力出问题会不会拖垮全系统？

## 一、隔离性：目前能给出什么保证

**诚实的回答**：因为今晚没有做物理卸载，**无法承诺"一个能力崩溃不影响其它能力"**。
所有能力仍运行在同一个应用进程里。

**但已经做到的是「编排层隔离」**：

| 保证 | 说明 |
|---|---|
| 运行时不碰业务数据 | 能力运行时只做"登记/发现/激活/暂停"，**不拥有任何业务状态**（有机器断言 RT-13 强制） |
| 未接入的能力不会被误激活 | 运行时会拒绝激活任何"未声明可激活"的能力（RT-06 断言） |
| 不允许停用安全/常驻能力 | 停用凭据、会话这类能力会被直接拒绝（RT-10 断言） |
| 启动失败不影响原有功能 | 能力层初始化包在错误捕获里，失败只记日志，应用照常启动 |
| 依赖缺失不会静默通过 | 强依赖没登记就拒绝解析（RT-04 断言） |

**还没有做到的**：进程级/模块级隔离（一个能力崩溃仍可能影响整体）——这是后续目标，不是现状。

## 二、恢复：6 个回滚点

每个阶段完成都会打一个**带说明的标签（annotated tag）**，随时可以退回：

| 回滚点 | 含义 |
|---|---|
| `semantic-governance-v1` | 上一阶段冻结基线（**总回滚点**） |
| `capability-phase7a-architecture-pass` | 能力架构审计完成（纯文档） |
| `capability-phase7b-contract-pass` | 能力契约与登记表完成 |
| `capability-phase7c-runtime-pass` | 最小运行时完成 |
| `capability-phase7d-pilot-pass` | 书签试点完成 |
| `capability-phase7e-resource-pass` | 资源治理完成 |

恢复方式走既有护栏脚本，不做危险的强制重置：

```bash
bash scripts/git-recover.sh        # 按护栏恢复
bash scripts/snapshot.sh --list    # 查看/对比快照
bash scripts/check-git-repo-integrity.sh --self-test
```
