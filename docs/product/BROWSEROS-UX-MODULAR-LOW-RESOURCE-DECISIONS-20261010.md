## 1. 本轮明确决策（不要再误解）

1. **产品是 BrowserOS，不是 Creator / 资产 Workbench V3。** BrowserOS 最重要的是「浏览器 + 文件资源管理器」，其他能力围绕这两个核心提供增量价值。
2. **把本轮讨论、分析、取舍、验收证据写成 Markdown 留在 GitHub 单一主仓库中。** 纯 Markdown 内容变更应走快速路径，不主动运行完整 Rust、构建、供应链及 GUI 门禁；只校验文档内容、引用、差异和仓库状态。已有 GitHub Actions 是否自动触发由仓库配置决定，不能靠口头承诺规避。
3. **代码变更仍要按变更面验证。** 前端布局改动至少覆盖相关导航/布局回归、构建及仓库规定的最低检查；原生 GTK/WebView、权限、安装包的高风险改动绝不能借文档豁免跳过实测。
4. **审美目标是现代、克制、清晰、人性化，比 ChatGPT、Trae、IntelliJ IDEA、VS Code 形成更适合本产品的体验。** 这是一项追求和评估标准，不是已证明的市场排名；不能靠堆积功能、阴影或动效来宣称胜出。
5. **高频即显、低频渐进、危险操作确认，支持鼠标和键盘。** 「平时少打扰，需要时不缺能力」；新手容易上手，熟练者可快速操作。
6. **像插件一样可拆卸，但不为了拆分而新建多个仓库。** 一个 GitHub 主仓库；Capability 按需装载、启停、缺席和故障隔离；区分代码模块、运行时启停与真实可独立安装的扩展包。
7. **省资源和稳定性优先于炫技。** 原生 WebView 数量、宫格、终端、资源采集、缩略图和长列表必须按需使用、可观测、可释放。宫格异常不能带崩普通浏览器或文件管理器。
8. **无人值守实施以已授权范围与真实证据为边界。** 不要求用户人工 PR 审核；不绕过服务器保护规则，不将静态代码检查等同真实桌面 GUI PASS。

## 2. 当前产品结构（源码审计，非全部实机验收）

当前审计登记 **23 个 Capability Manifest**；这个数字不等于 23 个主页面、23 个独立安装包，也不意味着每个能力均可安全运行时卸载。

现有八个物理界面区域：
1. 顶部统一页签栏：网页、目录、模块页签和窗口控制。
2. 主导航/工具栏：常用导航、地址栏（URL / 本地路径）、返回/前进/刷新、收藏、工具和设置。
3. 工具栏内联扩展行：菜单、历史/常用路径、宫格设置与归档。
4. 左侧工具区：工具导航、收藏/文件等上下文面板。
5. 中央主工作区：浏览器 / 宫格 / 文件管理器 / 各模块主页面。
6. 右侧 Dock：浏览时同时操作文件、终端、资源、会话（由能力贡献提供页签）。
7. 底部状态栏：当前视图、连接、资源、页签及操作反馈。
8. 按需弹层：命令搜索、确认、图片预览等；禁止用 HTML z-index 覆盖原生 WebView。

**功能归类与建议默认位置**

| 层级 | 能力 | 默认展示 |
| --- | --- | --- |
| P0 双核心 | 浏览器、文件管理器、URL/路径导航、统一页签 | 永久可发现；无需找复杂菜单 |
| 高频辅助 | 收藏/最近、主页、新建/关闭页签、返回前进、文件预览、右侧文件 Dock | 就近上下文呈现 |
| 条件高频 | 宫格/AI 群发、终端、会话恢复、下载/网页资源、剪贴板、知识归档 | 使用后记忆入口；不常驻占据主要注意力 |
| 中低频 | Git/仓库、命令/脚本、数据库、计划任务、应用、图谱、技能、智能体 | 命令搜索 + 工具中心/菜单 |
| 维护/诊断 | 插件、Capability Manager、工程健康、审计、性能选项、凭证配置 | 设置/模块中心；出问题时可直接抵达 |

已存在的重要基础：Contribution Registry 的多种 slot、WORKBENCH_MAIN 按 view 认领、BROWSER_DOCK 的可用页签动态渲染、部分页面的 defineAsyncComponent 懒加载，以及模块缺席后的视图回退。**保留并优化这些机制，不重写 Vue Shell。**

仓库指针：
- src/components/layout/UnifiedTabBar.vue：标签和窗口拖拽事件路径。
- src/components/layout/ActivityBar.vue：地址栏、一级入口、内联展开菜单。
- src/components/layout/MainArea.vue：动态能力页面和 Dock。
- src/components/layout/StatusBar.vue：状态与内存采集。
- src/stores/useLayoutStore.ts：导航菜单、分辨率密度和页签真源。
- src/capability/contribution/types.ts：插件贡献槽契约。
- src/styles/global.css、src/styles/tokens.css：当前外观和初期语义 token。

## 3. 用户旅程与操作频率（初始设计假设，须通过匿名本地采样/可用性测试验证）

这里的「高/中/低」是设计假设，不是已测得的真实用户频率。不得以此冒充量化结果。

| 场景 | 假设频率 | 首要目标 | 最短理想路径 | 容错与反馈 |
| --- | --- | --- | --- | --- |
| 打开网址 / 切换网页 | 极高 | 不意外增加标签或丢上下文 | 地址栏回车 → 当前页签导航；明确 Ctrl+T 新页签 | 标题更新、加载失败保留地址可重试 |
| 打开本地目录 | 极高 | 与网页一样自然 | 地址栏路径回车 → 当前空白页签复用或明确切目录 | 无效路径保留输入与错误说明；不可创建错误标签 |
| 查找、预览文件 | 极高 | 看得到当前位置和内容 | 文件入口 → 路径/目录树/列表/预览 | 大目录渐进呈现，不阻塞浏览器 |
| 开新页签 / 关闭 | 极高 | 不丢误操作的可恢复性 | 加号 / Ctrl+T / 中键；关闭无确认，Ctrl+Shift+T 恢复 | 不擅自自动保存会话，遵循既定锁定决策 |
| 收藏及最近访问 | 高 | 一眼找到常用网站和目录 | 地址栏旁收藏 / 聚焦最近项 | 历史脱敏，仅展示必要内容 |
| 边浏览边管文件 | 中高 | 不丢网页上下文 | 右侧文件 Dock → 操作 → 收起 | Dock 改变布局而非压住网页 |
| 宫格并行查看/AI 对比 | 条件高频 | 并行效率，不能拖垮主程序 | 独立入口 → 格数选择 → 开启 | 预算不足要解释；逐级降低格数，异常可单独恢复 |
| 开终端、Git、数据库等 | 中低 | 有需要时一步可达 | 统一命令入口/菜单/最近使用 | 首次加载提示；能力未安装不展示死入口 |
| 设置、诊断、模块启停 | 低 | 可理解、可恢复、不会误拆核心 | 设置 → 模块中心/资源诊断 | 启停前说明影响，保留停用前工作状态 |

使用频率影响：**优先级、是否常驻、快捷键、视觉密度、状态更新频率、初始化时机**；不能简单用「访问频率低」删除功能。

## 4. 建议的新信息架构（让每个像素都有意义）

### 4.1 常态桌面

- **第一行：统一页签条**。当前标签高亮；网页/文件夹/模块图标分辨但交互一致；标题随当前文档变化；右侧保留完整窗口控制和既有拖拽空白区。
- **第二行：通用操作栏**。左侧保留「浏览器」「文件管理」两个明确入口，必要时主页/宫格作为上下文可选；中间地址栏优先获得宽度；右侧保留收藏、文件 Dock、统一命令入口和少量常用动作。
- **默认隐藏第三行**；仅当操作明确要求时展开「最近访问」「功能菜单」「宫格配置」。这是正常文档流内联行，不是覆盖原生 WebView 的浮层。
- **中央占用最大空间**，WebView 宿主和文件列表不因装饰失去面积；文件管理的目录树、列表、预览为按需可调整分栏。
- **右侧 Dock 默认关闭或记住用户上次选择**，开启时改布局，不遮挡网页；只加载当前可见 Dock 内容。
- **底部状态栏只保留有决策价值的状态**：当前视图、真正的页签数、异常提示、应用内存概要。审计条数/仓库已配置等低频项进入详情，不常驻闪烁。
- **模块中心**集中展示「基础能力 / 可选能力 / 正在运行 / 占用与健康」，而不是把所有模块塞在一级导航。

### 4.2 视觉语言（以效率为前提）

- 统一暗/亮主题与语义色，不让导航浅色、状态栏深色、浮层第三套主题造成割裂；优先复用现有 token，并逐层扩展，不改变原生几何语义。
- 基础间距遵守 4px 网格；多用留白、细分隔、同类圆角和清晰层次，少用亮色块/Emoji 堆叠/厚阴影。
- 选中与焦点必须不只依赖颜色，键盘焦点清晰可见；加载、空状态、失败、禁用、危险操作各有明确语义。
- 工具提示：图标短 tooltip + 可见的「名称/作用/风险」。触屏/键盘环境不能依赖 hover 才发现关键操作。
- 禁止无意义自动滚动、成功 Toast、弹窗抖动和过度动画；遵从 prefers-reduced-motion。
- 两侧面板和地址栏设置最小宽度/溢出规则；缩窄时先折叠低频动作，但必须可由菜单和命令搜索到达。
- 超越竞品的方向不是模仿 UI：像 ChatGPT 一样低认知负担、像 Trae 一样强调 AI 工作流上下文、像 IDEA 一样有可靠导航及诊断、像 VS Code 一样可扩展，却把 **网页与本地文件自然连通** 作为差异化卖点。这是设计对标，而非未经测量的优劣结论。

## 5. 交互细节契约

| 输入/场景 | 正确行为 | 不能出现 |
| --- | --- | --- |
| 已有普通网页页签时地址栏输入 HTTP(S) | 在当前页签导航；用户明确新建才创建页签 | 每次 Enter 都新增标签 |
| 新建空白页签输入 URL/本地路径 | 复用当前空白页签或按已冻结标签语义替换 | 无意义连续新增空白/宫格标签 |
| 地址栏输入绝对目录 | 打开文件视图；路径不被当作网页；失败时有可恢复提示 | 重复创建目录页签、把路径提交给搜索引擎 |
| 页签标题更新 | 先保留 URL/目录名占位，随后以来自该 WebView 且 URL 匹配的 title 更新 | 把 A 页迟到的标题赋给 B 页、旧 title 残留 |
| 宫格入口 | 明确开启、布局、格数和资源代价；隐藏 ≠ 销毁，主动关闭按生命周期释放 | 打开宫格就改变其他页签的导航规则 |
| 网页右侧 Dock | Dock 开/关统一触发布局矩形更新 | float/fixed/z-index 盖住原生 WebView |
| 顶部操作栏 / 标题栏 | hover、active、focus、disabled 区分；拖拽空白仍可移动窗口 | 鼠标位于普通标题栏变十字/异常 resize、按钮区触发拖动 |
| 模块被停用或缺席 | 导航贡献立即收敛；打开的主视图回退到可用视图；释放订阅/定时器 | 死菜单、空页面、幽灵 PTY 或后台常驻 |
| 大目录/图片预览 | 元数据先行，缩略图仅可视项、并发 ≤4，缓存上限、切目录取消排队 | 一次性读所有原图、Pinia 塞满 base64 |
| 常用成功/失败 | 成功操作安静完成；失败进入状态栏/独立信息区，可重试 | 成功 Toast 干扰、HTML overlay 被网页挡住 |

**特别说明**：PR #16「Prevent stale browser tab titles and cross-tab attribution」在编写时仍处于开放状态，不要与其并行改同一标题生命周期代码。最终是否已合并必须重新查 GitHub。

## 6. 像插件一样装卸：架构契约

### 6.1 区分三个容易混淆的级别

- **源码模块化**：目录与导入边界拆分；并不代表可运行时卸载。
- **运行时 Capability 热插拔**：生命周期 enable / pause / disable / absent 与 Contribution 动态收敛，不等于操作系统独立安装包。
- **独立扩展包**：单独分发/更新/卸载、签名、权限和兼容性，需另立安装与沙箱契约；23 Manifest 不自动满足。

### 6.2 分层

- P0 Kernel：窗口布局真源、页签意图、原生 WebView host、文件管理核心、错误与恢复状态。用户不应能因误禁用可选插件而拆掉主程序。
- P1 内建可选能力：宫格、收藏、终端、会话、采集、知识归档、仓库、应用、剪贴板。
- P2 长尾工具：数据库、脚本、任务、图谱、技能/智能体、调试资源。
- P3 第三方扩展（目标）：版本化 Manifest / API / 权限 / 资源预算 / crash policy / compatibility；无审查不得执行任意高权限原生代码。

每个 Capability 必须能回答：**何时被加载、占用什么、允许做什么、如何暂停/恢复/完全停止、缺席后哪个入口收敛、状态如何恢复、失败会影响谁？**

### 6.3 可拆卸验收矩阵

| 操作 | 需要证明 |
| --- | --- |
| 从构建中缺席 | Shell 没有非法静态 import、死菜单、白屏；注册表能正常生成 |
| 运行时停用 | 贡献入口和定时任务取消，订阅/监听/资源释放；主程序存活 |
| 再启用 | 原状态可安全恢复，不重复注册、不重复监听；行为幂等 |
| 工作时崩溃 | 故障隔离在能力内部或子进程；核心浏览器和文件管理器可操作 |
| 低内存启动 | 按预算拒绝/降级宫格，不误删或破坏普通页签 |
| 取消/卸载 | 数据保留策略明确；不悄悄删除用户文档/凭据 |
| 无插件配置 | 基础浏览和文件操作闭环仍完整 |

注意：原生 WebView 的硬隔离能力不能靠 Vue 组件 error boundary 保证。高风险宫格必须以 Rust 子进程、主线程边界和桌面实机故障注入验证为准；不可在未经批准下更改 WebView hide/resize 时序。

## 7. 省资源是产品能力，不是隐藏内存数字

**执行方向**
- 启动只加载首屏所需数据、当前页签与当前面板；更多工具通过 Contribution 延迟 import。
- 文件目录先元数据 + 可见项；长列表虚拟化；预览按需获取、并发限制及 LRU 缓存。
- 资源统计用单实例采样器，失焦/隐藏降频，展开资源详情再升频；禁止多个 Dock/状态组件各自开启重复轮询。
- 宫格按需创建，明确格数与预计额外内存；非活动项按经过验证的 offscreen 路径维护，不许用 webview.hide() 或 1x1 调整触发历史死锁。
- 不可见资源 Dock / 图谱 / 编辑器 / 图片灯箱不提前初始化高开销内容。
- 在纯 JavaScript 页面不得用频繁 setInterval 强行驱动布局，布局变化归一到宿主定位单一入口；销毁时清理 ResizeObserver/listener/interval。
- 缓存要有尺寸上限、逐出策略和可观测指标，不能无限累积。

**性能 SLO：以下是提议验收门槛，不是实测现状。** 必须先收集冷/热启动、空闲 5/30 分钟、20 个普通页签、2/4/6 格宫格、大目录 1万项的 baseline（同机、同配置、同网站），记录中位数和 p95。

| 指标 | 建议初期闸门 | 状态 |
| --- | --- | --- |
| 无插件/纯基础能力冷启动到首个可交互页面 | 新版 p95 不高于基线 +5%；阶段性目标下降 20% | 未测 |
| 普通导航回车到实际当前页签响应 | p95 ≤ 基线，且 0 次意外新增标签 | 未测 |
| 文件万项列表首次可操作 | 首屏不等待全量缩略图、无主线程长任务 > 100ms | 未测 |
| 空闲 CPU 5min 后 | 较基线下降；无持续无意义 3s 轮询 | 未测 |
| 空闲 RSS（0/5/30min） | 无单调无界增长；与基线对照，并拆分主进程/子 WebView | 未测 |
| 4 格运行与关闭后 | 浏览/文件功能连续可用；资源逐步回收并量化 | 未测 |
| 卸载可选模块 | 入口、后台任务、监听器全部收敛，无残留 | 未测 |
| 可访问性 | 键盘可达、Esc 焦点回位、对比度与最小点击区域检查 | 未测 |

不要提供「比 VS Code 内存少」「比 IDEA 启动快」这类没有同机公平复测的断言。也不追求无意义的单数字：Linux WebKitGTK WebView RSS 与共享内存统计需要说明统计口径。

## 8. 实施顺序（一次性任务可并行开展，但合并遵守风险边界）

### 优先级 0：基础可靠性（禁止被视觉修改回退）

- URL、路径、空白页签、网页/模块切换与浏览器标题独立性；原生 WebView 坐标、窗口拖拽和宫格恢复。
- PR #16 避免重复修改；全套相关回归后再合并。
- 资源低内存/宫格崩溃时主程序仍可浏览网页和文件。

### 优先级 1：用户直接感知

## 12. 自适应外壳视觉理念：扩大视野，不牺牲可靠性（2026-10-10）

> 用户新决策：希望尽可能减少顶部页签/工具栏占高，支持快捷键全屏阅读与工作，减少过多入口；性能与稳定性优先。允许采用比简单模仿 Google Chrome 更好的独立方案。本节是正式产品目标，不表示相关代码均已实现。

### 12.1 我们的理念：「内容优先，工具随行，强大而安静」

浏览器与文件资源管理器是核心，工具和插件只在需要时出现。「更大视野」不是纯粹让工具栏消失，而是同时优化有效内容面积、导航可发现性、操作次数、键盘操作速度、可靠性和内存/CPU。禁止为了好看让日常任务更难完成。

**裁决：认可合并视觉边框，但不立即将页签条和地址栏硬拼成单行。** 采用 Adaptive Chrome（自适应应用外壳）：用一体化底色与轻分隔制造单一顶部界面、降低高度，再提供「标准／紧凑／沉浸」三档。Chrome 在此指应用窗口外壳，不是替换为 Google 浏览器内核。

为何否决直接物理合并：
- 页签很多时挤占地址栏；地址栏过长又导致页签无法辨认，用户要多次操作；
- 第一行负责窗口拖拽、双击最大化和系统控制，修改 DOM 结构可能回退鼠标事件；
- Linux 浏览器是原生子 WebView，调整顶部区域会触发视口矩形同步；不能像普通网页一样靠 CSS z-index、fixed 或 transform 覆盖；
- 原有下方内联扩展行正是为了避免菜单被原生 WebView 遮挡。

### 12.2 三种工作模式

| 模式 | 用户感受 | 保留什么 | 隐藏什么 | 默认 |
| --- | --- | --- | --- | --- |
| **标准** | 熟悉、清楚、高效 | 页签、地址栏、核心导航、窗口控件 | 低频专业按钮藏进工具中心 | 是 |
| **紧凑** | 小屏也宽敞 | 当前页签定位、地址栏与必要导航，窗口可拖动 | 次要操作、可选 Rail/Dock | 否 |
| **沉浸** | 最大限度阅读/编辑内容 | 内容本身、可恢复退出路径、必要系统状态 | 顶栏、侧栏、可选底栏和 Dock | 否 |

标准模式：上面仍是两行，但视觉连成一个整体；首行只管标签与窗口，第二行以地址/路径栏为主。通过减薄边框、压缩多余 padding 增加面积，不靠复杂动画。

紧凑模式：不做盲目的一行化。优先让地址栏完整可用；次要动作收纳在「工具」中。新手可以点击一个常驻或可发现的恢复控件回到标准模式；缩窄窗口时不能让窗口拖拽区域和关闭按钮消失。

沉浸模式：支持真正的操作系统窗口全屏，不能把隐藏 Vue 顶栏冒充系统全屏。全屏后仍能可靠退出，不能依赖主 Vue 窗口一定收到来自网页内原生 WebView 的键盘事件。

### 12.3 快捷键设计（目标，不是现成已实现）

| 操作 | 建议 | 注意事项 |
| --- | --- | --- |
| **F11** | 进入/退出系统全屏沉浸模式 | 经窗口 API 统一状态；原生子 WebView 获得焦点时也要有效 |
| **Esc** | 按层次关闭当前 UI 弹出内容；合适时退出沉浸外壳 | 不抢夺网页视频/游戏本身的 Esc 语义 |
| **Ctrl+L** | 随时找到地址栏并聚焦，沉浸时先恢复必要导航 | 不能因为工具栏已卸载导致无效 |
| **Ctrl+Shift+F11**（候选） | 标准与紧凑模式切换 | 先核对现有键位映射和系统快捷键冲突 |
| **Ctrl+K**（候选） | 统一查找网页、路径、命令与插件 | 应复用现有统一命令搜索，不新增第二套真源 |

保留鼠标显式入口；不要只允许快捷键操作。鼠标靠近屏幕上沿时**不默认**反复自动显隐工具栏，因为每次改变宿主几何都会影响原生 WebView。确有需求时只能在非覆盖式布局内按需展开，并做防抖及桌面验收。

### 12.4 源码核对出的现实与风险

- 当前 src/stores/useLayoutStore.ts 已有 compactMode 布尔状态和 toggleCompact；src/App.vue 在其开启时隐藏 UnifiedTabBar、ActivityBar 和 Rail。
- src/components/layout/MainArea.vue 目前仅在浏览器主视图显示「退出精简模式」按钮，切到目录/其他模块时恢复路径不够明显，属于待验证风险。
- src/components/layout/MainArea.vue 监控 compactMode 后调用 browser.relocate，说明顶部高度变化已有布局同步链路；严禁新增另一套互相竞争的原生位置计算。
- src/settings/state/useSettingsStore.ts 的 VS Code、IDEA、Eclipse 三种快捷键映射都没有 F11；src/App.vue 也没有对应全局事件，故**现在并不存在可宣告已完成的 F11 全屏功能**。
- 不改变既有窗口拖拽单一路径、GTK fixed move + size allocate、offscreen WebView 隐藏和普通标签关闭规则。

### 12.5 入口降噪方案：四种目的，而不是 23 个入口

默认只突出：
1. **浏览**：网页、标签、导航、收藏。
2. **文件**：目录、管理与预览（也能在浏览时打开文件 Dock）。
3. **快速查找**：唯一的全局搜索/命令入口，一处找网址、路径、功能。
4. **工具中心**：宫格、终端、Git、数据库、知识库、脚本、技能、智能体、插件和设置等按任务分类，不抢默认顶栏面积。

主页作为开始页/最近访问而不是额外抢占顶部按钮；宫格在确实经常使用时允许用户固定，但默认不要求每次浏览都初始化昂贵的多 WebView。已有模块**不删除功能**，只是统一入口、重新分层；隐藏一个图标不等于禁用模块，更不意味着释放内存。

避免重复：文件主页面和文件 Dock、终端主页面和终端 Dock、AI 导航和宫格、资源概要与资源详情、知识库和采集入口都应按「一个主要任务 + 一个上下文捷径」组织。插件不得默认向顶部永久加一个按钮；需用户固定，或有明确高频使用价值才能晋升。动态 Contribution Registry 仍是唯一插槽机制。

### 12.6 性能、安全和验收闸门

- 顶部常态采用普通 Flex/Grid 和简单背景/分隔，不引入 WebGL、Canvas、高频 JS 动画、永久 hover 轮询或重度全窗口毛玻璃。
- 模式切换必须一次修改布局偏好，等待布局稳定后再经既有 Browser Host 定位通道重新计算矩形；不额外创建 WebView、终端 PTY、重复监听或轮询。
- 不允许 HTML fixed 悬浮工具挡住 WebKit 原生网页；展开的控件占据正常布局空间。
- 导航贡献缺席时入口自动收敛；P0 浏览器、文件资源管理器不能被可选工具故障波及。
- 用真实 Linux 安装版测试普通网页、文件夹页签、宫格、多 Dock、长网址、窄窗口、窗口拖拽、焦点在原生网页内的 F11/Esc/Ctrl+L；检查 1 次切换只触发必要定位、不生成额外 tab。
- 实测对比三种模式的内容面积（绝对像素/占比）、模式切换延迟 p95、CPU/RSS 基线和失焦错误；未测量不得承诺「比 Chrome 更省内存」或「比 IDEA 更快」。

### 12.7 实施优先级与门禁规则

1. **视觉一体化**：只收敛上方两行背景、边界、间距和入口，保留窗口拖拽代码。优先做最小风险、可回滚的视觉改造。
2. **完整的紧凑/沉浸状态机**：任何视图都可以恢复；焦点和快捷键不冲突；避免重复 WebView 矩形重算。
3. **原生 F11 全屏**：涉及窗口 API/原生 WebView 键盘路径，必须有真机测试，不可只看 Vue 的 keydown。
4. **工具中心和插件入口策展**：设置可固定常用工具、快捷键发现、权限和资源占用清晰可见。
5. **每项验收保留前后对比**：截图、用例、峰值内存、空闲 CPU、失败恢复及真实 GUI 结果。

**文档变更走快速路径**：仅 Markdown 更新无需主动跑 npm check、Rust/供应链/GUI 门禁；代码变更仍遵守 AGENTS.md 的最低验证和真实桌面要求。当前本节只有设计决策和技术审计，未实施或验证三档新 UI、系统 F11 和入口收敛。
