# BrowserOS 项目实施经验与避坑记录

## 文档目的

记录 BrowserOS 在原型复刻、桌面集成、数据库、Git、智能体、模型配置、门禁和发布验收中的实际问题，避免后续把“代码通过”误判成“用户可用”。

## 一、最重要的验收原则

BrowserOS 的完成状态必须分层判断。以下为可能涉及的证据层级，不是每项任务都必须依序执行的发布流程：

```text
源码修复
  → 针对性测试
  → 前端 / Rust 构建
  → 安装包检查
  → 安装版 GUI 验收
  → 真实数据库 / Git / 模型 / MCP 验收
  → 提交、合并、推送远端
```

逐项报告适用范围及证据：代码检查使用 `CODE_PASS`，安装包检查使用 `PACKAGE_PASS`，真实桌面未验收使用 `GUI_PENDING`，用户明确完成桌面验收才能使用 `GUI_PASS`。真实服务未测试应注明待验证，存在实际阻断才使用 `BLOCKED`；不适用的项目注明“不适用”。一次性文档修改无需默认构建或安装；安装和远端操作以具体任务授权为准。

## 二、已踩过的主要坑

### 1. 原型与真实界面脱节

数据库、Git 和浏览器外壳曾出现“HTML 原型完成，但 BrowserOS 实际界面差异很大”的情况。

教训：原型必须作为真实实现的验收基准，不能只复刻颜色和标题，还要逐项核对布局、按钮、状态、输入、菜单、错误反馈和交互路径。

### 2. 把构建通过当成产品完成

`npm run build`、脚本检查和按钮静态检查只能证明代码或测试样例通过，不能证明安装版窗口可用、真实网页可用、数据库能连接或 Git 能写入。

教训：构建、安装包、安装版 GUI、真实服务联通必须分开报告。

### 3. 服务未启动就截图验收

曾出现访问 `127.0.0.1` 时 `Connection refused`，但仍尝试进行界面截图和验收。

教训：先确认进程、端口、实际 URL 和服务健康状态，再进行截图；服务没启动时必须先修复启动链路。

### 4. 智能体输入区的禁用原因不透明

输入框可以输入，但发送按钮因为“未打开项目”或“未选择模型”而禁用，界面没有明确说明，用户会认为输入功能失效。

教训：所有禁用按钮都要展示可见原因；快捷键触发失败时也要给出状态提示。智能体发送前至少要确认：

- 已打开项目；
- 已选择模型；
- 已建立或恢复会话；
- 没有待审批操作；
- 没有未处理的待审核变更。

### 5. 数据库连接没有形成真实闭环

曾出现 IDEA 导入数量不完整、账号密码没有完整导入、URL 解析失败、SSL 配置不合理、连接失败后表结构不可见等问题。

教训：数据库功能必须按真实流程验收：

```text
发现授权范围内的连接并报告数量 → 编辑账号 / 密码 → URL 解析 → SSL 协商
→ 建立连接 → 读取数据库 / 表 → 打开表数据 → 执行查询
```

应报告扫描范围、发现与可导入数量、跳过及失败原因；加密凭据、系统授权、驱动限制或重复项可能影响结果，不保证可导入全部连接或密码。不能用固定模拟数据代替真实数据库结果，也不能把未经验证的 TLS 降级当作安全连接。

### 6. Git 功能停留在模拟层

Git 原型可以展示提交、Diff 和冲突布局，但这不代表真实的 fetch、checkout、push、merge、rebase、文件编辑和冲突写入已经接入。

教训：必须明确区分“预览模式”和“真实 Git 写入”，并为每个按钮提供真实结果或明确的未实现状态。

### 7. 体积门禁与大型依赖冲突

Monaco 等大型编辑器加入后，继续用旧基线的 45% 总体积阈值会产生约 1531% 的误导性结果。

教训：大型依赖应采用独立预算：编辑器预算、核心共享预算和前端总量预算分别审核；历史基线增长保留观察，但不能伪称旧阈值通过，也不应为了追赶旧阈值破坏功能。具体生效额度以 [coding-editor-budget.json](coding-editor-budget.json) 和相关门禁为准，不把历史审批数字当成永久当前额度。

### 8. 重复运行昂贵检查

曾在输入未变化时反复执行完整构建、体积审计和合并门禁，浪费时间和 token。

教训：按改动范围选择检查：

- 日常修改：运行 `gate:quick` 或对应模块测试；
- 修改 Rust：运行 Rust 针对性检查；
- 修改智能体：运行 coding workbench、LSP 和模型边界检查；
- 最终收口：再运行一次完整门禁。

### 9. 模拟测试与真实模型测试混淆

fixture MCP、模拟审批、模拟传输和静态契约检查不能证明真实模型、真实 MCP 服务和真实安装客户端已经联通。

教训：报告中必须分别写清：

- 模拟测试结果；
- 本地代码检查结果；
- 真实模型请求结果；
- 安装版 GUI 结果；
- 尚未验证的边界。

### 10. 凭据处理边界不清

寻找 WorkBuddy、CodeBuddy 或其他本机模型配置时，最容易误把密钥写入日志、命令行、测试报告或 Git。

教训：

- 只读取明确配置来源；
- 不破解加密存储；
- 不打印密钥；
- 不把密钥写入源码、Markdown、日志或提交；
- 优先使用系统凭据存储；
- 找不到可用配置时写 TODO，不能无限重试。

### 11. 原生 WebView 与普通 DOM 的差异被低估

收藏夹菜单、Popover 和浮层不能简单依靠 HTML `z-index` 覆盖原生 WebView。

教训：涉及原生 WebView 时，必须单独验证原生菜单 / 原生窗口定位、窗口边缘、高 DPI、Wayland/X11 和缩放行为；不能用普通浏览器预览代替桌面验收。

### 12. 过度扩大修改范围

同时处理多个模块会扩大 diff 和验证范围，使问题更难定位。此前对某次具体扩展是否造成这些后果，尚缺少逐项可追溯的因果证据。

教训：坚持最小修改原则，只修复有证据支持的缺口；不要顺手升级架构或修改任务范围外模块。

### 13. Git 流程核对过晚

如果没有先确认当前分支、远端 URL、目标分支、工作树和提交历史，容易出现“本地完成但未合并”“推错远端”或“误把旧提交当成最新代码”。

教训：任何提交、合并、推送前都要核对：

```text
当前 branch
HEAD
工作树
remote URL
tracking branch
目标分支 HEAD
推送后 remote HEAD
```

## 三、可追溯案例与具体防范

### 真实模型把目标路径写成绝对路径

- 现象：隔离项目中的真实模型工具调用曾因目标文件使用绝对路径失败。
- 原因：当时工具说明未明确要求项目文件路径相对于项目根目录；原有路径边界继续生效。
- 证据与范围：[智能体验收记录](../tasks/browseros-agent-acceptance-todo.md)记录了补充契约后的 SenseNova 测试。模型读取合成技能与知识、请求夹具 MCP、提出文件变更，测试核验了实际磁盘文件及执行结果。
- 限制：审批由测试夹具完成，检查由测试程序发起；真实客户端审批、命令面板和安装版 GUI 未由该测试证明。
- 防范与通过标准：在工具契约中说明路径类型，保留越界拦截；使用隔离项目核对同一会话中的审批、最终文件、检查结果及会话恢复。

### DBX 原型按钮可点击，但结果不正确

- 现象：此前审核发现默认多行 SQL 无法运行、不同查询返回相同固定结果、格式化转义错误、CSV 换行和行数不正确、切换标签破坏布局，以及保存查询后无法恢复内容。
- 证据范围：这些是用户提供的此前审核结论；本文未重新运行当时版本，不能据此断言当前版本仍存在这些问题。
- 防范与通过标准：验证输入、实际结果、错误状态和恢复后的数据；检查下载文件内容及行数，并覆盖切换标签、主题和拖拽后的布局。演示数据应明确标注，不支持的 SQL 必须给出明确反馈。

### 安装完成后仍运行旧版本

- 风险：同版本包未覆盖、旧进程接管、desktop 入口指向错误文件，或应用加载了开发服务，都可能让用户继续看到旧界面；实际故障需逐项验证，不能仅凭症状确定原因。
- 依据：[项目安装验收规则](../../AGENTS.md)和 [PROJECT-RULES.md](../../PROJECT-RULES.md)。
- 防范与通过标准：核对包状态、desktop 入口、已安装二进制与包内哈希、运行进程路径和启动时间、实际窗口及加载地址；release 客户端应能独立于开发服务启动。截图通道不可用时标记 `GUI_PENDING`。

## 四、推荐工作流（按任务适用）

1. 阅读项目规则、任务文件和相关源码。
2. 只读核对当前分支、远端和工作树。
3. 先复现问题，保存失败证据。
4. 增加针对性回归测试。
5. 做最小代码修改。
6. 运行受影响模块的检查。
7. 需要合并或项目规则要求时运行完整门禁；复用输入未改变且仍有效的检查证据。
8. 涉及发布时构建 release 安装包，按授权检查安装入口、版本和二进制。
9. 有安装版验收要求且条件具备时，验证真实窗口、实际 URL 和交互；否则记录未验收原因。
10. 对任务涉及的数据库、Git、模型和 MCP 分别记录真实或模拟验收结果。
11. 涉及提交时检查密钥及 diff；按授权提交、合并、推送，并校验实际远端 HEAD。

## 五、禁止的错误结论

- “构建通过，所以安装版已经正常。”
- “按钮能点击，所以真实功能已经接入。”
- “原型页面完成，所以 BrowserOS 已经复刻完成。”
- “模型配置存在，所以真实模型闭环已经通过。”
- “本地 master 有提交，所以远端已经更新。”
- “截图通道不可用，所以可以用日志代替 GUI 验收。”

## 六、交付报告最低格式

每次交付至少说明：

1. 本轮实际修改了什么；
2. 哪些检查通过；
3. 哪些是模拟测试；
4. 哪些是真实运行结果；
5. 安装版 GUI 是否验证；
6. 是否已提交、合并、推送；
7. 剩余 TODO、阻断原因和恢复条件。

这份文档本身只记录经验和验收边界，不替代具体模块的产品需求或安全规则。
