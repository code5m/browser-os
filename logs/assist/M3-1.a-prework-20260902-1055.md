### 2.2 PTY 创建与 I/O（`bridge.rs:1917-2027`）

| 项 | 实现 | 位置 |
|---|---|---|
| 创建 | `native_pty_system().openpty(PtySize{rows:24, cols:100, pixel_width:0, pixel_height:0})` | `bridge.rs:1930-1938` |
| shell | `$SHELL`，回退 `/bin/bash` | `:1940` |
| 环境变量 | `TERM=xterm-256color`、`COLORTERM=truecolor` | `:1942-1944` |
| slave | `pair.slave.spawn_command(cmd)` 后 **立即 `drop(pair.slave)`** | `:1946-1950` |
| writer | `pair.master.take_writer()`，启动后写 `\n` 触发提示符 | `:1952-1954` |
| reader | `pair.master.try_clone_reader()`，交给 `std::thread::spawn` 死循环 `read` | `:1956-1983` |
| 输出推送 | reader 线程内 **直接** `app.emit("term-data", {id, data})`，4 KB buf | `:1973-1976` |
| 会话登记 | `AppState.terminals: Mutex<HashMap<String, TerminalSession>>` | `:1989-1993`, `:101-102` |
| `TerminalSession` | `writer: Box<dyn Write + Send>` + `child: Box<dyn portable_pty::Child + Send + Sync>`，**无 `impl Drop`** | `:113-117` |
| EOF 处理 | reader 线程 `Ok(0)` → break → emit `[终端已退出]` | `:1968`, `:1982` |

**判定**：PTY 创建/读写链路完整可用；**无 mpsc、无 pump task、无退避重试**——`Channel::send` / `emit` 在 reader 线程内同步调用，高吞吐时会反压 reader 线程（M3-1 的改造对象）。

### 2.3 resize —— **后端是空实现（实测）**

```rust
// bridge.rs:2011-2016
/// 调整终端大小（列/行）。
#[tauri::command]
pub fn term_resize(app: AppHandle, id: String, cols: u16, rows: u16) -> Result<(), String> {
    let _ = (app, id, cols, rows);   // ← 全部参数被吞掉
    Ok(())
}
```

- 后端 `term_resize` **不调用** `MasterPty::resize(PtySize)`。
- 前端 `src/bridge.ts:207-209` 定义了 `termResize()` 封装，但**全仓零调用方**（`grep -rn "termResize" src/` 仅命中定义本身）。
- `TerminalPane.vue` 只用 `FitAddon`（`:35-38, 52-55`），`fit.fit()` 只改变 **xterm 前端渲染尺寸**，不通知 PTY。

**判定**：**resize 链路完全断开**。表现：拖动窗口后 xterm 重新排版，但 PTY 的 `TIOCSWINSZ` 未更新 → shell 仍按 24×100 换行，`vim`/`top`/`htop` 等全屏程序显示错位。这是当前终端最明显的体验缺陷。

### 2.4 history / scrollback

| 层 | 情况 |
|---|---|
| 后端 | **完全没有 scrollback 概念**：reader 线程读到的字节直接 emit，不缓存、不限量 |
| 前端 xterm | `new Terminal({...})` **未设置 `scrollback`**（`TerminalPane.vue:22-34`），使用库默认值（xterm.js 默认 1000 行） |
| 历史上限常量 | **不存在**（项目中无 `TEMPORARY_HISTORY_LIMIT` 或同类常量） |
| 磁盘持久化 | 无 |

**判定**：scrollback 目前全靠 xterm 默认 1000 行兜底；后端无限推送 → 前端内存随输出量增长。fileterm 的 `TEMPORARY_HISTORY_LIMIT=40` 指的是"重连时回放的临时历史条数"，与 xterm scrollback 不是同一概念，引入前需先澄清语义（见 §5.R4）。

### 2.5 process ownership

| 问题 | 现状 |
|---|---|
| 谁持有 child | `AppState.terminals` 的 `TerminalSession.child` |
| 谁 kill | 只有 `term_kill`（`bridge.rs:2020-2027`）：`terms.remove(&id)` 后 `s.child.kill()` |
| kill 是否覆盖进程树 | ❌ **只 kill 直接子进程**（`Child::kill()`），不处理孙子进程（如 shell 里起的 `sleep`/后台任务） |
| reader 线程回收 | 靠 EOF 自然退出（`Ok(0)` → break），**无 join、无显式停止标志** |
| `TerminalSession` Drop | ❌ 无 `impl Drop`；`remove()` 后依赖字段自动析构（writer 关闭、child 句柄 drop，但**不会 kill**） |
| 页签关闭/组件卸载时 | `TerminalPane.vue:66-70` 只 `dispose()` xterm + 解绑 writer，**不调 `term_kill`** |
| 应用退出时 | ❌ **无清理**：`main.rs:591` `CloseRequested` 仅 `grid_manager.shutdown_all()`；`main.rs:674` `.run()` **无 `RunEvent` 分支**（只 `unwrap_or_else` 处理错误） |

**判定（最关键的一条）**：**关闭主窗口不会杀掉任何 PTY**。残留 = PTY master/slave + shell 进程树 + reader 线程。这与 #3「关闭窗口能否正确释放资源」是同一个缺陷的两个面。

> 佐证：`main.rs` 中 `std::process::exit` 出现 6 次（`:107/146/157/248/252/256/468/677`），hard exit 会跳过所有析构 → 更不可能靠 Drop 清理。

### 2.6 ShutdownCoordinator 接入点（**本盘点的核心产出**）

当前**不存在**任何退出协调器。推荐接入点（按改动风险从低到高）：

| 优先级 | 接入点 | 位置 | 做什么 |
|---|---|---|---|
| **P0-1** | 主窗 `CloseRequested` | `main.rs:591-593`（现仅 `grid_manager.shutdown_all()`） | 在同分支内追加 `bridge::shutdown_terminals(app)`：遍历 `AppState.terminals` 逐个 `child.kill()`（+ 进程组 kill），清空 map |
| **P0-2** | `TerminalPane` 卸载 | `TerminalPane.vue:66-70` | `onBeforeUnmount` 内调 `system.killShell()`（现只 `dispose()` xterm） |
| **P1-1** | `term_kill` 增强 | `bridge.rs:2020-2027` | kill 进程树（进程组）+ 等待 reader 线程结束（用 `AtomicBool` stop flag + `JoinHandle`） |
| **P1-2** | `TerminalSession` 加 `Drop` | `bridge.rs:113-117` | Drop 时 kill child，作为"漏网"兜底（**注意**：不能替代显式 kill，因 `std::process::exit` 不跑 Drop） |
| **P2-1** | `RunEvent` 分支 | `main.rs:674-678` 的 `.run()` | 加 `match event { RunEvent::ExitRequested {..} | RunEvent::Exit => { coordinator.shutdown_all() } _ => {} }` |
| **P2-2** | 独立 `shutdown.rs` | 新文件 | 统一收口：terminals / grid_manager / 后续 scheduler（M4-58.a）/ 脚本进程（M2-3.a）/ 插件（M5-15.a） |
| **P3** | `request_app_exit` 命令（M0-2） | `bridge.rs` 新增 + ACL | 前端可主动请求退出，走同一 coordinator |

> 顺序建议：**P0-1 + P0-2 先行**（改 2 处、风险极低、立刻消除 PTY 泄漏）；P1 与 M3-1/M3-2 同期做；P2/P3 与 M0-2 一起做。

### 4.1 `term_resize` 修复后的契约

```rust
#[tauri::command]
pub fn term_resize(app: AppHandle, id: String, cols: u16, rows: u16) -> Result<(), String> {
    // 1. 取 session（不存在 → Err("终端不存在")，不静默成功）
    // 2. master.resize(PtySize { rows, cols, pixel_width: 0, pixel_height: 0 })
    //    ⚠️ portable-pty 0.8 的方法名是 `resize`，不是 `set_size`
```

> 现状要求：`TerminalSession` 目前**未持有 `MasterPty`**（`bridge.rs:113-117` 只有 `writer` + `child`）。要修 resize，**必须先给 `TerminalSession` 增加 `master: Box<dyn MasterPty + Send>` 字段**——这是修 resize 的前置改动，也是本次盘点发现的关键隐藏工作量。

### 4.2 `TerminalSession` 目标形态（草案）

```rust
pub struct TerminalSession {
    pub writer: Box<dyn std::io::Write + Send>,
    pub child: Box<dyn portable_pty::Child + Send + Sync>,
    /// 【新增】PTY master：resize 需要（当前未持有 → resize 无法修）
    pub master: Box<dyn portable_pty::MasterPty + Send>,
    /// 【新增】reader 线程停止标志（配合 EOF 双保险）
    pub stop: Arc<AtomicBool>,
    /// 【新增】reader 线程句柄：term_kill 时 join，确保线程回收
    pub reader: Option<std::thread::JoinHandle<()>>,
}
```

### 4.3 ShutdownCoordinator 草案接口

```rust
// src-tauri/src/shutdown.rs
pub struct ShutdownCoordinator {
    ran: AtomicBool,          // 幂等：重复调用只执行一次
}

impl ShutdownCoordinator {
    pub fn shutdown_all(&self, app: &AppHandle) {
        if self.ran.swap(true, Ordering::SeqCst) { return; }   // 幂等
        bridge::shutdown_terminals(app);        // PTY 进程树 + reader 线程
        app.state::<AppState>().grid_manager.shutdown_all();   // 宫格子进程（已有）
        // 【后续挂载点】
        // scheduler.abort();                    // M4-58.a
        // script_runtime.cancel_all();          // M2-3.a
        // plugin_runtime.unload_all();          // M5-15.a
    }
}
```

**幂等是硬要求**：`CloseRequested` 与 `RunEvent::Exit` 可能都触发，重复执行不得 panic 或二次 kill 已清理的 map。

## 5. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **关主窗不杀 PTY** → 孤儿 shell + reader 线程常驻 | **高** | P0-1 + P0-2 先行（改动极小） |
| R2 | `term_kill` 只杀直接子进程 → 孙子进程残留 | **高** | 进程组 kill（`setsid` + `killpg`）或递归 kill；用 `ps --ppid` 实测验证 |
| R3 | 修 resize 需先改 `TerminalSession` 结构（新增 master 字段） | 中 | 结构改动要一次性做完；`master` 与 `writer` 都来自同一个 `pair.master`，注意 `take_writer()` 后仍可 `resize()`（需实测确认 portable-pty 0.8 行为） |
| R4 | `TEMPORARY_HISTORY_LIMIT` 语义混淆（fileterm 的重连回放 vs xterm scrollback） | 中 | 引入前先定义清楚"我们要的是重连回放还是 scrollback 上限"，不要照抄 |
| R5 | 高吞吐下 `emit` 同步阻塞 reader 线程，反压 PTY | 中 | mpsc(128) + pump task（M3-1 本体）；改造时注意保留 §2.7 的 `termBuffer` 竞态处理 |
| R6 | `std::process::exit` 硬退出跳过析构，`Drop` 兜底不可靠 | 中 | 显式 kill 为主，Drop 仅兜底；P2-1 的 `RunEvent::Exit` 分支是唯一可靠时机 |
| R7 | 引入 tokio 增加依赖与二进制体积 | 低 | 优先 `std::sync::mpsc` + `std::thread`；确需异步再评估 |
| R8 | 改 `TerminalPane.vue` 卸载逻辑可能影响"切换面板后重连"的既有体验 | 中 | 明确区分"隐藏面板"与"销毁终端"；当前 `terminalOpen=false` 只隐藏不 kill，需保持 |
| R9 | 死依赖 `strip-ansi-escapes` 与 M0-6 的 gtk/wry 清理混在一起改 | 低 | 分开 commit，各自独立验证 |
