## 4. 协议草案

### 4.1 能力清单（Capability Manifest）

**原则**：对外暴露的能力 = 既有 59 个命令的**子集**，**不新建执行层**。首期只暴露只读/低危能力。

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct CapabilityManifest {
    pub app: String,              // "mvp-browser-os"
    pub version: String,          // 语义化版本
    pub protocol_versions: Vec<String>,   // ["a2p/0.1-draft", "mcp/2025-06-18"]
    pub capabilities: Vec<Capability>,
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct Capability {
    pub name: String,             // 如 "artifact.list"
    pub description: String,
    /// 映射到内部命令（一对一，不新增逻辑）
    pub maps_to: String,          // 如 "list_artifacts"
    pub risk: RiskLevel,
    /// 是否需要用户在确认闸门中批准
    pub requires_confirm: bool,
    /// 是否需要显式策略开关才可用（默认关闭的能力）
    pub requires_policy: Option<String>,
    pub params_schema: serde_json::Value,  // JSON Schema（首期可为简化描述）
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, PartialOrd)]
#[serde(rename_all = "snake_case")]
pub enum RiskLevel { Read, Write, Execute, Dangerous }
```

**首期能力白名单（建议，逐条对应既有命令）**：

| 能力名 | maps_to | risk | requires_confirm |
|---|---|---|---|
| `artifact.list` | `list_artifacts` | Read | 否 |
| `artifact.read` | `read_artifact` | Read | 否 |
| `audit.list` | `audit_log` | Read | 否 |
| `repo.list` | `list_repos` | Read | 否 |
| `workspace.list_dir` | `list_dir` | Read | 否 |
| `workspace.read_file` | `read_file` | Read | 否 |
| `tab.list` | `tab_list` | Read | 否 |
| `db.query`（若 M4-14.a 完成） | `db_query` | Read | 否（受§4.4 策略限制） |

**首期明确不暴露（无论配置如何）**：
- `write_file` / `create_file` / `delete_path` / `rename_path`（写文件）
- `launch_app` / `open_browser`（打开外部程序/URL）
- `request_sync` / `confirm_sync`（出网推送）
- `term_write` / `term_spawn`（终端 = 任意命令执行）
- `script_*` / `run_script`（M2-3.a 的执行通道）
- `db_*` 的写路径
- `clipboard_*`（剪贴板可能含敏感信息）

> 理由：这些能力一旦暴露，"外部 Agent 提示词注入"可直接转化为本地任意操作。**M5 首期不开放执行类能力。**

### 4.2 A2P（Agent → Protocol / 本应用作为被调用方）

**首期传输**：**stdio**（子进程模式），**不开 TCP 端口**。

理由：
- 避免本地监听端口带来的局域网暴露面（历史上多个 MCP 实现的 0day 都源于默认监听 `0.0.0.0`）。
- 进程生命周期与被调方绑定，退出即回收（与 M3-1.a 的进程回收议题一致）。
- 鉴权简化为"谁能启动这个进程"。

| 项 | 契约 |
|---|---|
| 传输 | stdio（stdin/stdout），**UTF-8**，换行分隔 JSON（NDJSON / JSON-RPC 2.0） |
| 协议 | **MCP 2025-06-18**（用 `rmcp` 纯 Rust 实现，**禁 npm 分包**） |
| 启动方式 | 外部 Agent 以 `--mcp-server` 参数启动本应用（需新增 argv 分支，参考现有 `--grid-child` 模式，`main.rs` 已有先例） |
| 消息上限 | 单条请求 ≤ 1 MB；单条响应 ≤ 5 MB（超出截断并标记） |
| 并发 | 单进程串行处理（首期）；并发留待稳定后 |
| 超时 | 单请求 30s |

**消息形态**（JSON-RPC 2.0，`method` 前缀为能力名）：

```jsonc
// 请求
{ "jsonrpc":"2.0", "id":1, "method":"artifact.list", "params":{} }
// 成功
{ "jsonrpc":"2.0", "id":1, "result":{ "artifacts":[ /* ... */ ] } }
// 失败（错误码见 §4.5）
{ "jsonrpc":"2.0", "id":1, "error":{ "code":-32001, "message":"FORBIDDEN",
  "data":{ "capability":"artifact.list", "reason":"policy_denied" } } }
```

### 4.3 A2A（Agent ↔ Agent，二期）

| 项 | 契约（草案） |
|---|---|
| 定位 | 二期，依赖 A2P 稳定后再做 |
| 方向 | **双向**：本应用既可作为任务发起方（委派给外部 Agent），也可作为接收方 |
| 消息模型 | `A2aTask` + `A2aMessage`（见下），幂等键必填 |
| 能力发现 | 复用 `CapabilityManifest`，通过对方 manifest 端点获取 |
| 任务状态机 | `submitted → working → completed / failed / canceled`（对齐 A2A 社区规范的状态命名） |
| 鉴权 | 双向：本地侧校验调用方 token（keyring 存），远程侧校验对方身份 |
| **红线** | A2A 接收的**任何内容都视为不可信输入**，要触发执行必须过本地确认闸门 |

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct A2aTask {
    pub id: String,                    // uuid v4
    pub idempotency_key: String,       // 调用方提供，用于去重
    pub requester: String,             // 发起方标识
    pub capability: String,            // 请求的能力名
    pub params: serde_json::Value,
    pub status: A2aTaskStatus,
    pub created_at: DateTime<Utc>,
    pub updated_at: DateTime<Utc>,
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "snake_case")]
pub enum A2aTaskStatus { Submitted, Working, Completed, Failed, Canceled }
```

### 4.4 `McpGlobalPolicy`（护栏，**fail-closed**）

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct McpGlobalPolicy {
    /// 全局只读：开启后所有 risk > Read 的能力一律拒绝（**默认 true**）
    pub read_only: bool,
    /// 允许危险 SQL（默认 false；且与 M4-14.a 的 `allow_write` 需同时为 true 才生效）
    pub allow_dangerous_sql: bool,
    /// 允许的数据库连接白名单（默认空 = 不允许任何 db 能力）
    pub allowed_connection_ids: Vec<String>,
    /// 允许的能力名白名单（默认 = §4.1 首期白名单）
    pub allowed_capabilities: Vec<String>,
    /// 结果行数上限（默认 50；对齐 dbx 的 EXECUTE_QUERY_LIMIT 思路）
    pub result_limit: usize,
    /// 是否允许"需要确认"的能力自动放行（**默认 false = 必须人工确认**）
    pub auto_confirm: bool,
}
```

**判定顺序（任一失败即拒绝，不短路跳过后续检查）**：
1. 能力是否在 `allowed_capabilities` → 否 → `CAPABILITY_NOT_ALLOWED`
2. `read_only` 且 `risk > Read` → `READ_ONLY_MODE`
3. 能力需要 `requires_policy` 且该策略未开 → `POLICY_DISABLED`
4. 若能力是 `db.query`：`allow_dangerous_sql` 与 `allowed_connection_ids` 双重校验
5. `requires_confirm` 且 `auto_confirm=false` → 走两段式确认闸门（对齐 `request_sync`/`confirm_sync` 范式）
6. 通过后执行 → **写 `audit.json`** → 结果按 `result_limit` 截断

### 4.5 错误码

| 码 | 含义 | 客户端该怎么做 |
|---|---|---|
| `-32700` | JSON 解析失败 | 修正格式 |
| `-32601` | 未知 method | 查 manifest |
| `-32001` | `FORBIDDEN`（策略拒绝） | 不要重试，属配置问题 |
| `-32002` | `CAPABILITY_NOT_ALLOWED` | 同上 |
| `-32003` | `READ_ONLY_MODE` | 同上 |
| `-32004` | `CONFIRM_REQUIRED`（需人工确认） | 提示用户去 UI 确认 |
| `-32005` | `RESULT_TRUNCATED`（非错误，附在 data 中） | 收窄查询条件 |
| `-32006` | `RATE_LIMITED` | 退避重试 |
| `-32007` | `INTERNAL_ERROR` | 上报，附带 run_id 供查审计 |

### 4.6 审计契约

- **每次能力调用都写 `audit.json`**（这是红线，不允许"只读调用不记审计"）。
- `action` 命名：`mcp_call`、`a2a_task_receive`、`a2a_task_send`。
- `detail` 含：`capability`、`requester`、`policy_snapshot`（当时策略值的摘要）、`result`（success/denied/error）、`run_id`。
- ⚠️ **与 M4-58.a §4.5 的同一问题**：若调用频繁会刷空 1000 条上限。建议同样做**独立文件 + 摘要进 audit**（`mcp-calls.json`），策略与定时任务保持一致。

## 5. 风险

| # | 风险 | 等级 | 缓解 |
|---|---|---|---|
| R1 | **提示词注入**：外部 Agent 通过被处理的网页/文档内容诱导本应用执行危险操作 | **极高** | 首期不暴露任何执行类能力（§4.1 黑名单）；A2A 输入一律不可信；执行类能力若未来开放，必须人工确认 |
| R2 | MCP Server 监听 TCP 端口 → 局域网任意主机可调 | **极高** | 首期**仅 stdio**，不开端口；若未来必须开，只能绑 `127.0.0.1` + token 鉴权 |
| R3 | 协议层绕过既有的 ACL / 确认闸门 / 审计 | **高** | 协议层**不直接调内部函数**，只能调"能力 → 命令"映射，命令层仍受 ACL 与闸门约束（§4.4 判定顺序） |
| R4 | 下沉 `phantom-core` 造成 workspace 冲突 | 中 | 现有两个独立 workspace（`src-tauri` + `tauri-browser-tabs`），下沉前需先明确边界；Cargo 禁止未排除的嵌套 workspace |
| R5 | A2A 双向带来的身份伪造 | 中 | 双向 token（keyring 存）；不入日志/审计 |
| R6 | 自动化调用刷空 `audit.json` | 中 | §4.6：独立调用日志 + 摘要进 audit |
| R7 | `rmcp` 引入增加依赖与编译时间 | 中 | 记录构建耗时/体积，对比 `logs/baseline-2026-08-27.md`；必要时做成 optional feature |
| R8 | 协议版本演进导致兼容破裂 | 低 | manifest 里声明 `protocol_versions`；首期按 draft 实现并显式标注"草稿，可能变" |
| R9 | 结果集过大经协议传输撑爆内存 | 中 | `result_limit=50` + 单响应 5 MB 上限 + 截断标记 |
| R10 | 误以为"A2P 已实现"就开放执行能力 | **高** | 本草案明确：首期能力白名单**不含任何执行类**；放开需单独评审 |
