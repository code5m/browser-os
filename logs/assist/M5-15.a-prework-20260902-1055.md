### 2.1 关键判断

- **"插件"在本项目中有三种可能形态，权限模型差别巨大**：

| 形态 | 执行体 | 权限模型复杂度 | 备注 |
|---|---|---|---|
| **① 声明式插件**（包一层脚本/工具/Skill） | 复用既有执行通道 | 低 | 推荐首期 |
| **② HTML 工具插件** | webview 渲染 + JS | 中 | 与 M2-7.b 同源；`withGlobalTauri=true` 是红线风险 |
| **③ 原生动态库插件**（`.so`/`.dll`） | 进程内代码 | **极高** | 建议**永不实现** |

**建议：首期只做 ①，明确排除 ③。** ③ 的 `dlopen` 会完全绕过 Rust 类型系统与所有 ACL，等于把安全边界交给插件作者。

- **`withGlobalTauri = true` 是本次盘点的红线发现**：若插件（尤其形态 ②）运行在继承了全局 Tauri 对象的 webview 中，可直接 `window.__TAURI__.invoke(...)` 调任意已注册命令，权限模型形同虚设（与 M2-7.b §5.R3 是同一问题）。

## 4. 权限模型

### 4.1 Manifest 结构

```rust
/// 插件形态（首期只支持前两种）
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "snake_case")]
pub enum PluginKind {
    /// 包装一个脚本（M2-3.a 的 ScriptMeta）
    Script,
    /// 包装一个 HTML 工具（M2-7.b 的 ToolMeta）
    Tool,
    /// 包装一个 Skill（M5-12.a 的 SkillDef）
    Skill,
    /// 会话处理器（#14，尚未实现）
    SessionHandler,
    /// ❌ 明确不支持：NativeLib（动态库）
}

/// 权限等级（累进：高等级隐含低等级权限）
#[derive(Debug, Clone, Serialize, Deserialize, PartialEq, PartialOrd, Eq, Ord)]
#[serde(rename_all = "snake_case")]
pub enum PermissionLevel {
    /// 只读：调用 Read 级命令
    Read,
    /// 写：调用写命令（每次需确认闸门）
    Write,
    /// 执行：跑脚本/命令（每次需确认闸门 + 审计）
    Execute,
    /// 网络：出网请求（每次需确认闸门 + 审计）
    Network,
}

/// 细粒度权限声明（在等级之上进一步收窄）
#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "snake_case")]
pub enum PluginPermission {
    /// 允许调用的具体命令名白名单（**优先于等级**）
    Commands { allow: Vec<String> },
    /// 允许读写的文件系统根目录（必须显式列出）
    FsRoots { paths: Vec<String> },
    /// 允许访问的网络目标（host 白名单，**不支持通配**）
    NetHosts { hosts: Vec<String> },
    /// 允许访问的数据库连接（引用 M4-14.a 的 conn id）
    DbConnections { ids: Vec<String> },
    /// 允许使用的 keyring 条目前缀（**不暴露凭据本体**）
    KeyringPrefixes { prefixes: Vec<String> },
}

#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct PluginManifest {
    pub id: String,               // 反向域名或 slug，全局唯一
    pub name: String,
    pub version: String,          // 语义化版本
    pub description: String,
    pub author: Option<String>,
    pub kind: PluginKind,
    pub entry: String,            // 相对插件目录的入口（脚本路径 / HTML 文件）
    /// 声明的权限等级（安装时展示）
    pub level: PermissionLevel,
    /// 细粒度权限（可缺省；缺省表示"仅按等级判定"）
    pub permissions: Vec<PluginPermission>,
    /// 配置 schema（JSON Schema，首期可为简化描述）
    pub config_schema: Option<serde_json::Value>,
    pub homepage: Option<String>,
}

#[derive(Debug, Clone, Serialize, Deserialize, PartialEq)]
#[serde(rename_all = "snake_case")]
pub enum PluginState { Installed, Enabled, Disabled, Error { reason: String } }
```

### 4.2 权限判定算法（**fail-closed**）

```
can_invoke(plugin, command) -> Allow | RequireConfirm | Deny
  1. 命令是否在 ACL 白名单（default-commands.toml）？
     否 → Deny(COMMAND_NOT_IN_ACL)
  2. 命令是否在 plugin.permissions 的 Commands{allow} 中声明？（若声明了该 permission）
     否 → Deny(NOT_DECLARED)
  3. 命令的 risk 等级 ≤ plugin.level 对应的等级？
     否 → Deny(LEVEL_EXCEEDED)
  4. 命令是否涉及文件系统？路径是否在 FsRoots 内（canonicalize 后前缀校验）？
     否 → Deny(FS_OUT_OF_ROOT)
  5. 命令是否出网？目标 host 是否在 NetHosts（精确匹配，不支持通配）？
     否 → Deny(NET_HOST_NOT_ALLOWED)
  6. 命令是否需要确认闸门（risk > Read 或命令本身带闸门）？
     是 → RequireConfirm（走两段式 confirm）
  7. → Allow，且**写审计**
```

**硬规则**：
- **默认拒绝**：任何未显式声明/未通过任一步的调用一律 `Deny`，不允许"警告但执行"。
- **声明 ≠ 授予**：manifest 里声明的权限在安装时展示，**必须用户确认后才写入授权记录**。
- **运行时以授权记录为准**，不以 manifest 为准（防止插件作者事后改 manifest 提权）。
- 路径判定必须 `canonicalize()` + 前缀校验（防 `..` 与软链接逃逸，与 M2-1.a §4.5 规则 2 同源）。
- 网络 host **不支持通配符**（`*.example.com` 属高危通配，需明确列出具体 host）。

### 4.3 授权记录（Grant）与确认流程

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct PluginGrant {
    pub plugin_id: String,
    /// 用户实际授予的等级（可低于声明等级）
    pub granted_level: PermissionLevel,
    pub granted_permissions: Vec<PluginPermission>,
    pub granted_at: DateTime<Utc>,
    /// manifest 内容哈希：manifest 变更 → 授权失效，需重新确认
    pub manifest_hash: String,
}
```

**安装流程（对齐既有 `request_sync`/`confirm_sync` 两段式范式）**：

```
1. plugin_install(path)
   → 解析 manifest → 校验结构 → 计算 manifest_hash
   → 生成 InstallPreview { plugin_id, name, level, permissions, 风险说明 }
   → 写审计 action="plugin_install_request"
   → 返回 preview（**不安装**）

2. 前端展示权限清单（用户看到"该插件将能：读文件 / 执行脚本 / 访问 example.com"）

3. plugin_confirm_install(preview_token, 用户勾选后的实际授权)
   → 落盘插件文件 + 写 PluginGrant（含 manifest_hash）
   → 审计 action="plugin_install"
   → 状态 = Installed（**默认 Disabled**，需用户显式启用）
```

**默认 Disabled 是硬要求**：安装不等于启用，避免"装了一堆插件，重启后全部自动跑起来"。

### 4.4 提权与变更

| 场景 | 处理 |
|---|---|
| 插件更新后 manifest 权限**扩大** | `manifest_hash` 变化 → 授权**失效** → 插件自动置 `Disabled` + 提示重新授权 |
| manifest 权限**缩小**或仅版本号变化 | 仍需重算 hash；建议同样要求重新确认（保守） |
| 用户修改授权（降低等级） | 立即生效；已授予的高权限动作停止 |
| 插件被禁用 | 所有调用 `Deny(PLUGIN_DISABLED)`，资源释放 |
| 插件卸载 | 删文件 + 删授权记录 + 审计；**保留审计历史**（不删） |

### 4.5 审计契约

每次插件行为都写 `audit.json`，`action` 命名：

| action | 时机 |
|---|---|
| `plugin_install_request` | 生成 preview |
| `plugin_install` | 用户确认安装完成 |
| `plugin_enable` / `plugin_disable` / `plugin_uninstall` | 状态变更 |
| `plugin_invoke` | 插件调用命令（含 `plugin_id`、`command`、`decision`） |
| `plugin_invoke_denied` | **被拒绝的调用也要记审计**（这是发现恶意插件的关键线索） |

`detail` 含 `plugin_id`、`command`、`decision`（allow/confirm/deny）、`reason`。
⚠️ 与 M4-58.a §4.5 / M5-7.a §4.6 同一问题：插件高频调用会刷空 1000 条上限 → 建议 `plugin_invoke` 走独立日志 + 摘要进 audit。
