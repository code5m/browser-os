## 1. 第一组：输出上限（taskcard 4 MB/5000 行 vs prework 256 KB）

**裁定：双层上限，总缓冲 4 MB（或 5000 行，先到先算），单 run 落盘尾留存 256 KB。**

理由：
- 运行期**内存**上限必须收紧（R9：100 MB 输出不能撑爆应用）。taskcard 的「环形缓冲 4 MB / 5000 行」是**内存中保留窗口**，对应 R9 防 OOM；prework 的 256 KB 是**落盘历史尾存**，二者是不同层级，并非互斥。
- 因此不二选一，而是明确分层：
  1. **内存环形缓冲**：上限 `RING_MAX_BYTES = 4 * 1024 * 1024` 或 `RING_MAX_LINES = 5000`（先到先算），单片 ≤ `CHUNK_MAX_BYTES = 8 * 1024`，事件节流 30 ms（对齐 taskcard §4.8）。
  2. **落盘运行记录尾存**：`SCRIPT_RUN_TAIL_BYTES = 256 * 1024`，超出丢弃头部并置 `truncated = true`（对齐 prework §4.5 + M2-3.a §5 给 M2-4 的「只写 output_tail 前 200 字符」审计约束）。
- **落盘截断不依赖内存环形**：运行记录写入独立文件（§4.7），即使内存环形已丢旧片，落盘尾存仍按 256 KB 保留「最后一段」。
- 审计**不得**写输出正文（M2-3.a §4 红线 + M2-3.a §5 给 M2-4 的约束）；只写 `script.run.finish` 的 `truncated` 布尔与 `duration_ms`/`exit_code`。

## 2. 第二组：超时默认值（taskcard 60s vs prework 300s）

**裁定：全局默认 `DEFAULT_TIMEOUT_SECS = 60`；`ScriptMeta.timeout_secs = 0` 表示用全局默认；脚本级上限 `MAX_TIMEOUT_SECS = 600`。**

理由：
- `ScriptMeta.timeout_secs` 已在 M2-3 落库且注释为「0 = 使用全局默认（300）」。但若直接把全局默认定为 300，则与 taskcard §4.6 的 60s soft 默认冲突，且会让「未显式配置的脚本」默认跑 5 分钟——对受控脚本库偏宽松。
- **裁决修正 M2-3 注释口径**：全局默认取 **60s**（更保守，契合「受控例外」定位），`ScriptMeta.timeout_secs` 注释中「300」改为「60」；因该字段是 `#[serde(default)]` 且当前无落盘数据，无迁移成本。脚本作者需更长超时时显式在 `ScriptMeta` 设 `timeout_secs`（≤600）。
- 分层（对齐 taskcard §4.6）：
  - soft = `effective_timeout`（全局默认或脚本级，封顶 600）。
  - hard = soft + `HARD_GRACE_SECS = 5` → `SIGKILL`。
  - 取消 = `SIGTERM` → 等 `CANCEL_GRACE_SECS = 5` → `SIGKILL`。
  - 状态区分：`Timeout` vs `Cancelled`（终态不可互转，见 §4.7）。

## 3. 第三组：并发上限（prework 8 vs taskcard R14 的 10）

**裁定：同 `script_id` 禁止并发（返回 `SCRIPT_ALREADY_RUNNING`）；全局并发总数上限 `MAX_CONCURRENT_RUNS = 8`。**

理由：
- taskcard R14「高并发跑 10 个脚本互不干扰」的语义是「不同脚本并发不互相阻塞」，**不是要求上限≥10**。prework 的「总数上限 8」是资源护栏（进程/线程/FD）。二者可同时为真：8 个**不同**脚本并发跑，每个脚本自身不重复触发。
- 因此 `MAX_CONCURRENT_RUNS = 8`（全局护栏），R14 用例改为「并发跑至多 8 个**不同**脚本互不干扰；第 9 个并发被拒 `TOO_MANY_RUNS`」。
- 同 `script_id` 并发：`run_script` 入口查进程表，已存在 `Running` 记录 → `SCRIPT_ALREADY_RUNNING`（对齐 prework §4.5 + M2-3.a §5 R12）。

## 4. 第四组：平台范围与降级策略

**裁定：M2-4 只实现 Unix（Linux）分支；非 Unix 平台 `run_script` 直接返回明确 `UNSUPPORTED_PLATFORM` 错误，文档标注能力缺口。**

理由：
- `setsid`/`killpg` 是 Unix-only；Windows 需 Job Object、macOS 需签名后行为校准，二者均无实测证据（release 仅在 Linux 验证）。
- 最小化风险：b 卡用 `#[cfg(unix)]` 实现进程组，非 unix 用 `#[cfg(not(unix))]` 桩返回错误，不写半成品 Windows 逻辑（避免开「看似可用实则无回收」的口子）。
- 不在 M2-4 做 Windows Job Object；若后续要跨平台，单开检查点（同 M2-4 的「逐张展开」原则）。

## 5. 第五组：env 策略（env_clear + 最小集 vs 允许 ScriptMeta 声明白名单）

**裁定：M2-4 采用 `env_clear()` + 固定最小集；`ScriptMeta` 不加 env 白名单字段（后续按需单开）。**

固定最小集（不可配置）：
```
PATH=/usr/local/bin:/usr/bin:/bin
HOME=<app_data_dir 父>
LANG=C.UTF-8
TERM=dumb
```
理由：
- 最小攻击面优先（防 `LD_PRELOAD`/`IFS`/`SSH_AUTH_SOCK` 泄露）。taskcard §4.3 同口径。
- 不继承宿主环境；`ScriptMeta` 不加 `extra_env` 字段——避免把能力缺口变成「可配置后误开」。若实测有脚本依赖代理/locale，单开检查点评估白名单机制（同 §4 逐张展开原则）。
- `PATH` 固定闭集，脚本只能调用白名单路径内的解释器与工具（解释器本身来自 `ScriptInterpreter` 枚举，见 §6）。

## 8. 执行通道核心契约（b/c/d 共同依据）

### 8.1 命令构造（P0，核心安全契约）

```
❌ 禁止：Command::new("sh").arg("-c").arg(format!(...)) / bash -c / 任何字符串拼接
✅ 必须：
   Command::new(interpreter_bin)              // 来自 ScriptInterpreter 枚举映射，非用户输入
       .arg(script_abs_path)                  // canonicalize + allowed_roots 前缀校验
       .args(ordered_param_values)            // 每个值独立 argv 元素（shell 不重解析）
       .current_dir(locked_cwd)               // 脚本文件所在目录 canonicalize 后，非用户可控
       .env_clear()                           // §5 固定最小集
       .stdin(Stdio::null())                  // 默认不交互
       .stdout(Stdio::piped()).stderr(Stdio::piped())
```

- 解释器映射（白名单，来自 `ScriptInterpreter`）：`Bash→bash` / `Sh→sh` / `Python3→python3` / `Node→node` / `Shebang→直接执行脚本文件`（依赖可执行位+shebang）。**绝不接受用户输入的解释器字符串**（M2-3.a §0 第 2 条）。
- 参数顺序：严格按 `ScriptMeta.params` 声明顺序；**键名不进命令行**（键名仅展示/校验；R3 防 `--flag` 注入：键名已在 `validate_param_name` 限 `[A-Za-z0-9_]`，且值经 `validate_param_value` fail-closed）。
- `raw=true` 参数（仅 Path/Enum）：跳过单引号包裹，但仍过 `..`/超长检查（M2-3.a §3）。

### 8.2 cwd 锁定

- 默认 cwd = 脚本文件所在目录（`canonicalize` 后），**用户不可控**；Path 类型参数只作 argv，不改变 cwd（prework §4.5）。
- cwd 必须在 `allowed_roots` 内（复用 `check_path_within_roots`）。

### 8.3 超时与取消（分层，见 §2）

- soft `effective_timeout`（全局 60 或脚本级 ≤600）→ `SIGTERM` 给进程组。
- hard `soft+5s` → `SIGKILL` 给进程组。
- 取消：`SIGTERM` → 等 5s → `SIGKILL`；`status=Cancelled`。
- 幂等：对已终态 `run_id` 调 `cancel_script` → `Ok(())` 无副作用（R13）。

### 8.4 进程组回收（Unix）

```rust
#[cfg(unix)]
fn spawn_in_new_group(cmd: &mut Command) -> io::Result<Child> {
    use std::os::unix::process::CommandExt;
    unsafe { cmd.pre_exec(|| { libc::setsid(); Ok(()) }); }
    cmd.spawn()
}
#[cfg(unix)]
fn kill_group(pgid: i32, sig: i32) { unsafe { libc::killpg(pgid, sig); } }
```
- 顺序强制：`setsid` → 记 `pgid=child.id()` → `killpg(pgid, SIGTERM)` → 5s → `killpg(pgid, SIGKILL)` → `waitpid` 防僵尸。
- 禁止只 `child.kill()`（留孤儿）；非 unix 桩不实现回收（§4）。
- `pgid` 假设不成立（少数平台）时：降级为「kill 直接子进程 + 尽力扫描子进程树」并记录能力缺口（taskcard §7 中风险缓解），不在 M2-4 做 Windows Job Object。

### 8.5 输出背压（见 §1 双层）

- 独立线程读 stdout/stderr，不阻塞主线程/UI。
- 内存环形 4 MB / 5000 行；单片 ≤8 KB；事件节流 30 ms（`script-output` 事件 `{runId, chunk, seq}`，seq 单调递增）。
- 背压：前端久不消费 → 丢最旧 + `truncated=true`。
- `script-finished` 事件 payload = `ScriptRunResult`（终态）。
- 二进制：`String::from_utf8_lossy`，不做 ANSI 过滤。

### 8.6 退出收口（ShutdownCoordinator）

- M2-4.d 在 `register_shutdown_tasks` 注册 `kill-running-scripts`（**追加在 `shutdown-grid` 之后**，作为最后一道）：
  - 遍历进程表全部 `Running` → 走取消路径（`SIGTERM`→`SIGKILL`）→ 标记为 `Cancelled` 并落盘。
  - 超时宽限：coordinator 全局宽限沿用 M0-2 约定；脚本 kill 自身 5s grace 内完成，不阻塞退出主流程。
- 注册顺序变为：`stop-background-workers → flush-sessions → close-tabs → kill-terminals → shutdown-grid → kill-running-scripts`（新增最后一项，不改动既有 5 项顺序，避免 M0-2.d 测试矩阵归因错乱）。
