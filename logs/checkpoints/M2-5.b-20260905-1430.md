## 2. 四组分歧裁定（ADJUDICATED）

### 2.1 mock vs 直接接真实执行 → 直接接真实执行（不产 mock）

- **裁定**：b 卡直接调 `bridge.runScript(id, values)`，订阅真实 `script-output`/`script-finished` 事件；**不产任何 mock 执行器**（死代码，M2-3 先例）。
- **理由**：M2-4 已有真实进程级取证；a 卡已交付完整 CRUD；接真实执行无额外前置。

### 2.2 `script_runs_list` 是否新增 → 归 M2-5.c（b 不混入后端读命令）

- **裁定**：b 用既有 `script_status`（内存快照，不含输出正文）做运行态查询与对账，**不新增后端命令**；历史态数据源（`script_runs_list` 读 script-runs.json）单开 M2-5.c。
- **理由**：避免 UI 卡夹带后端命令审查；与 a/b/c 拆分口径一致。

### 2.3 D15（`script.validate.reject` 审计）前置归属 → b 内补（硬前置）

- **裁定**：**由 M2-5.b 内补**，且为 **PASS_CRITERIA 硬条件**。
- **实现位置**：`bridge.rs` 的 `run_script`，在 `start_run` 返回 Err（含参数校验失败）时，emit `script.validate.reject` 审计，detail 含 `script_id` / `param_name` / `error_code`，**不含参数值明文**（沿用脱敏三重保险）。
- **理由**：M2-4-ACCEPT §7 已判「须限期」；一旦有 UI 用户可控参数即可触达 `build_argv`，缺审计=失去攻击尝试可观测性。

### 2.4 输出节流分层（D14）→ 两层都补

- **裁定**：**后端补 30ms + 前端 rAF 合并**，两者都到位 D14 才归零。
- **后端**（`script_runner.rs::spawn_output_reader`）：同一 `run_id` 的 `script-output` 发射前做 30ms 节流合并（seq 仍单调，chunk 取末尾）；不丢数据，仅合并 IPC 频率。
- **前端**（`RunPanel`）：用 `requestAnimationFrame` 合并输出 chunk 的 DOM 更新，避免高频小量输出打满渲染。
- **理由**：只补前端，高频输出仍打满 IPC（D14 实质未解）；只补后端，UI 仍卡顿。两层互补。

### 2.5 正文落盘边界（沿用 a）→ 前端只传正文，路径后端生成

- **裁定**：b 执行阶段沿用 `script_body_path`（后端按 `<id>.<ext>` 生成 + 三重校验），前端不参与路径构造。a 已实现。
