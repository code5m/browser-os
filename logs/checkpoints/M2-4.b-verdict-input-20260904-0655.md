## 2. §3.1【必裁 · P0】argv 引号：`M2-4.a §8.1` 内部自相矛盾

### 2.1 冲突的准确表述（**比展开卡 §2.1 更深**）

展开卡只写了「加引号会把 `'` 字面量传进脚本」。核原始材料后，冲突实为**两条互斥技术路线被同时写进冻结契约**：

- **`M2-4.a §8.1` 主契约（P0 红线）**：
  > ❌ 禁止：`Command::new("sh").arg("-c").arg(format!(...))` / 任何字符串拼接
  > ✅ 必须：`Command::new(interpreter_bin).arg(script_abs_path).args(ordered_param_values)` —— 「每个值独立 argv 元素（**shell 不重解析**）」

- **`M2-4.a §8.1` 末条**：
  > `raw=true` 参数（仅 Path/Enum）：**跳过单引号包裹**，但仍过 `..`/超长检查

- **`M2-3.a §3` 原始裁定**（单引号包裹的来源）：
  > `raw` 的定义期合法性：`raw = true` 且 `param_type ∉ {Path, Enum}` → 保存元数据即拒绝。理由：`raw` 意味着**跳过单引号包裹**，只允许出现在取值域可控的类型上。
  > **单引号包裹策略属 M2-4**：本卡只提供 `raw` 标记与定义期校验，不实现拼接。

**矛盾**：单引号是 **shell 语法**。它的唯一作用是告诉 shell「不要解析这段内容」。若走 argv 数组（shell 不参与），单引号**既无必要也有害**——它会作为字面量进入脚本。反之，若坚持单引号包裹，就等于默认命令行会经过 shell 解释，与 P0 红线（禁 `sh -c`）直接冲突。

**§4.2 实测**已在本环境验证：`argv 传参: "'foo'"`（引号保留）、`shell 拼接: 'foo'`（引号被剥离）。

### 2.2 三条可选路线（**请逐条表态**）

#### 路线 A：argv 数组 + 一律不加引号，`raw` 保留但 no-op

- 做法：`build_argv` 对所有参数不加引号；`ScriptParam.raw` **保留字段**与定义期校验，在 argv 模式下不产生差异，注释标注「argv 模式下无效果」。
- 支持：①改动最小，不动 M2-3 已落库结构；②安全由「argv 数组 + `validate_param_value` 九条 fail-closed」保证，**不依赖引号**；③fail-safe 方向。
- 反对：留下一个**看起来有用、实则 no-op** 的字段。未来若有人基于 `raw` 做安全假设（「设了 raw 就不会被转义」），会踩坑。

#### 路线 B：保留单引号包裹（即维持 `M2-3.a §3` 原意）

- 做法：`build_argv` 对 `raw=false` 的参数加 `'...'`，`raw=true` 跳过。
- 支持：与 `M2-3.a §3` 字面一致。
- 反对（**强烈**）：①引号是 shell 语法，argv 模式下会作为字面量传给脚本（实测 §4.2），`Path` 参数会被脚本读到带引号的路径 → **真实功能 bug**；②若为了让引号生效而改走 shell 拼接，则直接违反 `M2-4.a §8.1` 的 P0 红线（禁 `sh -c`），等于用「防注入的引号」去救「本来就不该存在的 shell 拼接」，是本末倒置。
- **若裁定选 B，请明确回答**：是否同时推翻 `M2-4.a §8.1` 的 P0 红线？若是，需说明放弃 argv 数组的理由。

#### 路线 C：argv 数组 + 不加引号 + **废弃 `raw` 字段**

- 做法：同 A，并额外从 `ScriptParam` **移除** `raw` 字段，同步改 `domain.rs`、`scripts.rs::validate_meta`（去掉 `INVALID_RAW_PARAM` 规则）与可能受影响的 M2-3 门禁夹具。
- 支持：①不留下 no-op 字段，符合「不留看起来有用实则无效的能力」；②`raw` 在 argv 模式下**永远**不会有语义，留着就是误导；③`raw` 是 `#[serde(default)]` 且当前无落盘脚本数据，迁移成本近零。
- 反对：①动 M2-3 已冻结并落库的结构，需重跑 M2-3 门禁（含其 17 个坏样本夹具，`SCR_*` 码位若锚定 `raw` 需同步）；②扩大 b 卡改动面，与「逐张展开」原则略有张力（可另行单开检查点）。

### 2.3 影响面

| 路线 | 影响 |
|---|---|
| A | `build_argv` 实现 + 注释；B5 测试（值含引号时原样保留） |
| B | `build_argv` 实现 + **B5/R1~R5 全部需改写**；可能需修订 `M2-4.a §8.1` P0 红线 |
| C | A 的全部 + 改 `domain.rs`/`scripts.rs` + 重跑 M2-3 门禁 + 可能需单开「废弃 raw」检查点 |

## 3. §3.2【必裁】b 卡 stdio：中间态 vs 提前上 drain

### 3.1 冲突

`M2-4.a §8.1` 最终形态为 `.stdout(Stdio::piped()).stderr(Stdio::piped())`，但 §9 边界把「输出背压/环形缓冲/事件流」划归 d 卡。b 卡处于两难：

- 上 `piped` 而不读 → 子进程写满管道后**阻塞**（§4.3 实测：父进程不读时子进程 3 秒后仍卡在 `write` 无法退出）。Linux 默认管道容量 **64 KiB**（§4.1 实测；注意 `/proc/sys/fs/pipe-max-size` = 1 MiB 是**上限**不是默认值）。
- 上 `null` → 与最终契约不符，形成中间态，需依赖 d 卡接管。

### 3.2 三条可选路线

#### 路线 A：b 卡 `Stdio::null()`，d 卡改 `piped` + reader（**实现者倾向**）

- 支持：①严格不越界（输出属 d 卡）；②b 卡的 B7/B8/B9 是**生命周期**测试（sleep/超时/进程树），用不到输出。
- 反对：①中间态，若 d 卡忘记接管则出现阻塞（已在展开卡 §7 登记为移交项，但仍是依赖人的纪律而非机制）；②b 卡阶段无法验证「有输出的脚本能正常跑完」这一真实场景。

#### 路线 B：b 卡就上 `piped` + **只丢弃的 drain 线程**（不做背压、不保留、不发事件）

- 做法：spawn 时对 stdout/stderr 各起一个线程，`read` 后直接丢弃；代码量约 15 行；d 卡把「丢弃」替换为「环形缓冲 + 事件 + 尾存」。
- 支持：①**消除中间态**，最终形态的管道结构 b 卡就位，d 卡只换 sink，不存在「忘记接管」的风险；②b 卡阶段即可验证「持续输出 2 MB 的脚本能正常结束」，把 §4.3 的阻塞风险变成 b 卡的回归测试；③drain 不保留、不做背压、不发事件，**不构成**「实现 d 卡的背压」。
- 反对：①b 卡碰了输出相关代码，形式上轻微越界（需裁定者判断是否接受「drain 不等于背压」）；②多了 2 个线程/run（8 并发 = 最多 24 线程），需登记。

#### 路线 C：b 卡上完整环形缓冲 + 背压

- 反对：明确越界做 d 卡的活，且会让 b 卡 diff 过大不利于裁定复核。**不推荐**，列出仅供完整性。

### 3.3 影响面

| 路线 | 影响 |
|---|---|
| A | 无额外代码；依赖 d 卡接管（移交项已在展开卡 §7 登记） |
| B | +2 drain 线程；新增 1 项测试「持续输出脚本能正常结束」；d 卡只需替换 sink |
| C | 越界，b 卡 diff 翻倍 |

## 5. 实测证据附录（**均可在本环境复跑，鼓励裁定者自行验证**）

### 5.1 默认管道容量

```
$ python3 -c "import os,fcntl; r,w=os.pipe(); print(fcntl.fcntl(w,1032))"
默认管道容量 = 65536 字节 = 64 KiB
$ cat /proc/sys/fs/pipe-max-size
1048576        # 这是上限，不是默认值
```

### 5.2 argv 模式下单引号是字面量

```
$ python3 -c "import subprocess; print(repr(subprocess.run(['printf','%s',chr(39)+'foo'+chr(39)],capture_output=True,text=True).stdout))"
argv 传参: "'foo'"          # 引号保留，脚本会收到带引号的值
$ python3 -c "import subprocess; print(repr(subprocess.run('printf %s '+chr(39)+'foo'+chr(39),shell=True,capture_output=True,text=True).stdout))"
shell 拼接: 'foo'           # 引号被 shell 剥离
```

### 5.3 piped 而父进程不读 → 子进程阻塞

```
$ python3 -c "..."   # 子进程持续写 ~2 MB，父进程刻意不读
3 秒后子进程 poll() = None    # None = 仍存活，阻塞在 write
结论: 阻塞 —— 父进程不读时子进程卡在 write，无法退出
```
