## 二、根因分析

### Bug A：term-throughput 报告文件删除竞态（主因，导致 4/4 吞吐样本失败）

- **现象**：term-1 应用日志显示 `cycle 1 report ok`，但脚本侧报告文件消失、driver.result 未写出。
- **根因**：`spawn_m0_app` 对所有驱动统一传 `M0_CYCLES = 5(预热) + VR_CYCLE_SAMPLES(2) = 7`。而 term-throughput 的架构是**脚本逐样本独立 spawn**（1 预热 + 3 正式 = 4 次独立启动），前端每次启动只驱动一轮 10 MiB 负载。Rust 驱动按 `M0_CYCLES=7` 循环，第 2 轮开始每轮先 `remove_file(report)` 再空等 300s——脚本与驱动对同一文件形成删除/等待竞态。
- **修复**：`spawn_m0_app` 对 `term-throughput` 恒传 `M0_CYCLES=1`（`085854f`）。
- **教训**：**一个参数两处语义**。资源循环（tab/grid/terminal）是「单进程多轮」，吞吐是「多进程单轮」，共用 spawn 函数时循环数语义不同。参数应按驱动类型分流，而不是假设所有驱动同构。

### Bug B：terminal 资源循环第 3 轮偶发卡死（未复现）

- **现象**：驱动日志停在 `cycle 2 done`，第 3 轮无 done、无 FAIL、无 panic，90s 超时。
- **排查**：单独复现 `M0_DRIVER=terminal M0_CYCLES=7` → 7 轮全 PASS；会话日志无 panic；脚本采样路径不干预应用进程。判断为正式跑时序/系统负载相关的偶发（前序 grid 阶段刚结束，进程/FD 压力较高）。
- **处置**：在 `term_spawn`/`term_kill` 各步骤加日志（`085854f`），后续两轮正式跑 terminal 均 7/7 通过。若完整 20 样本基线复现，日志可直接定位卡在哪一步。
- **教训**：**偶发挂死第一时间是加可观测性，不是猜**。失败分支有 done 标记（`82ddb3b` 的设计）已证明价值——这次卡死能精确定位到「第 3 轮内部」，靠的就是标记 + 日志的边界。

### Bug C/D：证据一致性缺陷（PASS 后自查发现）

- summary.md 指标表**硬编码 BLOCKED**，与 summary.json 的 PASS 矛盾——而文件自述「两者不一致时整批 FAIL」；
- `frame_gap_p95` 空值经 Python `print(None)` 输出为 `None`（非法 JSON）；`driver_selfcheck.json` 用 printf 拼接、detail 含未转义双引号（非法 JSON）。
- **教训**：**手写 JSON 字符串拼接必然泄漏**。凡含外部数据的 JSON 一律走 `json.dump`；人类可读文件与机器判定文件必须同源生成或条件渲染，不能两份硬编码。

## 四、可改进

1. **环境提示里的「快速 run」参数未贯穿**：`spawn_m0_app` 的 `M0_CYCLES` 拼接是上个会话埋的雷，本应在联调 term-throughput 时按驱动类型审查参数。
2. **等待轮询超工具超时**：两次 `sleep 240+` 被 300s 工具超时截断，长等待应分段。
3. **terminal 卡死的压力变量未控制**：未验证「grid 刚跑完→terminal 卡死」的相关性假设；完整基线（20 样本）是更好的试金石。
