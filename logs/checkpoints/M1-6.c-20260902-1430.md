## 2. 复核结论（按严重度）

### 2.1 缺陷（已修复，F1）：切换分支后工作区/索引与目标树不一致

- **现象**：从 `other` 切回 `master` 后，仅存在于 `other` 的文件仍留在工作区与索引，
  `git_status` 凭空出现一条「added」，后续全量 `commit` 会把别的分支的文件一起提交。
- **根因**：旧实现「先 `set_head` 再 `checkout_head(safe)`」——`checkout_head` 以**新 HEAD**
  为基线，旧分支独有的文件对它而言等同「未跟踪」，既不会被移除、索引条目也保留；
  且 checkout 失败时 HEAD 已经移动，构成部分动作。
- **修复**：改为「先 `checkout_tree(目标树, safe)`（以索引为基线）再 `set_head`」，
  并对 `set_head` 极端失败做工作区回滚。
- **实证（探针，同仓库同场景）**：

| 方案 | 干净切换后 files / index | 脏冲突 | 未跟踪同名文件 |
|------|--------------------------|--------|----------------|
| A 旧（set_head→checkout_head） | `[a.txt, other.txt]` / `[a.txt, other.txt]` ❌ | HEAD 已移动 ❌ | 留下未跟踪文件、HEAD 切换 ⚠ |
| B（set_head→checkout_tree） | `[a.txt, other.txt]` / `[a.txt, other.txt]` ❌ | 同上 ❌ | 同上 ⚠ |
| **C 新（checkout_tree→set_head）** | `[a.txt]` / `[a.txt]` ✅ | 报错且 HEAD 不动 ✅ | 报错且 HEAD 不动 ✅ |

- 附带修复：未跟踪目录（如 `newdir/y.txt`）与目标分支文件（`newdir/x.txt`）共存时
  旧实现会误拦截，现按 git CLI 语义放行（见测试 T-gw-c-3）。

### 2.2 小修（F2）：全量 commit 的审计 `path_count` 恒为 0

`job.paths` 对全量提交为空，审计却用 `job.paths.len()` → 永远记 0，违背
「审计字段至少含 path_count」的要求。改为 `execute_git_write` 返回实际影响路径数
（全量提交取执行前 `read_status().len()`），成功审计用该值；失败审计沿用请求路径数。

### 2.3 小修（F3）：过期待确认任务无清理

未被 confirm 的任务只在再次 confirm 时才移除，会随用户反复 request 累积。
新增纯函数 `purge_expired_git_jobs`（只清理已过期项），在 request 插入前调用。

### 2.4 复核通过项（无需改动）

- 白名单：17 种黑名单操作串（reset/push/merge/rebase/stash/clean/cherry-pick/branch -D…）
  全部在 request 阶段返回「操作禁止」，零写入。
- 来源校验：两阶段命令均 `check_invocation_source`；request 阶段无任何 `sync::write_*`
  直写路径（闸门不可绕过）。
- 路径锁定：`repo_dir` 命中 `repos.json` + 拒逃逸；写原语各自再校验一次（先校验后执行，
  `index.write()` 只在全校验通过后调用 → 混合合法/非法路径零部分写）。
- 凭据隔离：写段（sync.rs:526+）无 `KeyringStore` / `cred_cb` / `token` / `Command::new`
  / `.push(` / `find_remote(` / `.fetch(` / `.merge(` / `reset(`（全文仅成果推送段
  1–244 行出现凭据，17 项黑名单 API 扫描为空）。
- 审计脱敏：`git_write_audit_detail` 签名只接收 op/repo_id/job_id/path_count/confirmed/extra，
  实现不含路径清单、diff、凭据；错误串 300 字节截断且不切 UTF-8。
- 闸门语义：一次性取出、5 分钟过期、dangerous 需二次确认且未确认时任务不取出（零执行）。
- discard 安全性：仅显式已跟踪路径，未跟踪文件整体拒绝（防误删新文件）；
  unstage 不删除工作区文件（已补测试固化）。
- 注册完整性：`main.rs` + ACL 各 2 处，前端类型与六个便捷封装齐备（无 UI，归 M1-7）。

## 6. 裁定：M1-6.d（push）——**保留**

结论：保留 M1-6.d，按 M1-6.a 冻结的 W3 继续实现非 force 推送；NEXT=`M1-6.d`。

理由：
1. **契约已冻结**：M1-6.a 的 W1/W2/W3 白名单与「b/c/d 三卡全绿才签 M1-6 整体 PASS」
   的口径已冻结，取消 push 属缩权，须由契约修订卡或新任务书显式改，不得由复核卡私自取消。
2. **能力缺口真实存在**：既有 `push_artifacts` 只推送 `artifacts/` 下的成果文件，
   不覆盖用户在 M1-6 里自选路径的提交；没有 push，本地提交无法同步远端。
3. **风险可控且设计已就绪**：非 force、二次确认（dangerous）、凭据仅推送瞬间读 Keyring、
   复用既有 `sync.rs push` 封装、审计脱敏——M1-6.a §4/§5 已给出完整口径。

附加硬约束（写入 d 卡任务书，不得由实现卡放宽）：
- 禁 force / `--force-with-lease` / `--mirror` / 删除远端分支；
- 复用 `sync.rs:241 push` 与 `cred_cb`，禁止另建凭据路径；token 不得落日志/审计/前端错误串；
- 必须 `dangerous=true` + `confirmed_dangerous=true` 双闸门；
- 推送失败须审计 `git_write_failed` 且可重新 request 重试（job 一次性）；
- 不得改既有 `push_artifacts` 链路。

## 7. 遗留风险（本卡不处理，须由后续任务书/负责人裁决）

1. **TOCTOU（全量 commit）**：预览在 request 时生成，confirm 时全量 `add_all` 会把
   request 之后新增的文件一并提交。收敛需「预览快照绑定」（把预览路径写入 job 并在执行时
   校验超集），属契约级变更，本卡不擅自实现。
2. **并发写无互斥**：同一仓库的多个已确认 job 在后台线程并行执行，无仓库级锁
   （既有 `push_artifacts` 同口径）。任务一次性 + 5 分钟过期已压缩窗口，互斥留待后续卡。
3. **符号链接边界**：仓库内符号链接指向仓库外的场景未做专项拦截（写原语按普通路径处理）。
4. **端到端 IPC 联调仍缺**：本机未配置仓库、本卡无 UI，未做真实 invoke 联调（归 M1-7）。
5. **M1-6.d 排序**：若负责人希望先做 M1-7 UI 再补 push，需由任务书改序；本卡保持契约顺序。
