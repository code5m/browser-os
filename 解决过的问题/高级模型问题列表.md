# 一、🔴 高级模型级问题

## 1. HTML 浮窗、Toast、关闭确认框被网页遮挡

**现象：**

- “已新建页签”的黑色提示框显示异常。
- 关闭页签时，确认框被网页盖住。
- 无论把 CSS 的 `z-index` 调多高，仍可能被遮挡。

**真正根因：**

浏览器页签不是普通 DOM 元素，而是 Linux 下的**原生 GTK/WebKitGTK 子 WebView**。

窗口结构实际上是：

```text
Tauri 主窗口
├── Vue / HTML 主界面
└── GTK 原生子 WebView
```

原生子 WebView 在窗口系统层级高于主界面的 HTML，所以：

```css
z-index: 999999;
```

也不能让 HTML 弹窗压到原生 WebView 上面。

**错误但很容易想到的方案：**

```css
.modal {
  z-index: 999999;
}
```

这种方案只能解决同一个 DOM 渲染层中的问题，解决不了两个原生窗口之间的层级问题。

**最终解决方式：**

显示关闭确认框时：

```text
用户点击关闭页签
    ↓
设置 closeDialogOpen / webviewsSuspended
    ↓
暂停原生 WebView 的持续定位
    ↓
临时隐藏或移开原生 WebView
    ↓
显示 Vue 的关闭确认框
    ↓
用户选择保存 / 删除 / 取消
    ↓
恢复或销毁对应 WebView
    ↓
强制重新计算宫格和网页位置
```

涉及的代码层包括：

```text
src/App.vue
src/components/browser/SessionCloseDialog.vue
src/composables/useBrowserHost.ts
src/stores/useBrowserStore.ts
src/stores/useLayoutStore.ts
src-tauri/src/bridge.rs
tauri-browser-tabs/.../platform/linux.rs
```

**为什么属于高级模型级：**

因为必须先否定“这是普通 CSS 层级问题”，然后识别：

- DOM 层
- Tauri 主 WebView
- GTK 原生子 WebView
- Linux 窗口层级
- 弹窗生命周期

这是典型的跨框架、跨语言、跨窗口系统问题。

**状态：**

- ✅ 用户已确认关闭框完整可见。
- ✅ 不再依赖 `z-index` 解决原生遮挡。
- 🧪 点击“取消”后网页恢复，自动检查通过，但用户人工验收记录不完整。

## 2. 多页签后出现外壳纵向滚动条、界面尺寸漂移

**现象：**

- 页签越来越多后，应用最右侧出现纵向滚动条。
- 弹窗位置被挤到异常位置。
- 页面整体似乎比主窗口多出几像素。
- 单纯设置页签栏 `overflow-y: hidden` 不能完全解决。

**真正根因：**

程序在创建多个原生页签以后：

- 每个子 WebView 的尺寸被持续校正；
- 但主界面的原生物理尺寸只在启动时校正一次。

也就是：

```text
子 WebView：持续同步尺寸
主界面：只启动时同步一次
```

长期运行、多页签切换或窗口变化后，两者产生布局漂移，最终让 HTML 主界面认为自己比可视区域更高，于是产生外壳纵向滚动条。

**最终解决方式：**

同时处理两层：

### 原生层

持续校正主界面的：

```text
native layout
physical size
size allocation
```

相关修改落在：

```text
src-tauri/src/bridge.rs
tauri-browser-tabs/.../platform/linux.rs
tauri-browser-tabs/.../platform/mod.rs
```

### 前端层

对主壳层设置明确的尺寸和溢出边界：

```css
html,
body,
#app {
  overflow: hidden;
}
```

同时保证浏览器页面自己的滚动条不受影响。

**为什么属于高级模型级：**

因为纵向滚动条只是表面症状。真正原因不是普通 CSS，而是：

- 原生窗口尺寸
- CSS 视口尺寸
- 物理像素
- 逻辑像素
- 多 WebView 布局更新频率

之间发生不一致。

低阶模型大概率只会反复增加：

```css
overflow: hidden;
```

这样可能把症状藏住，却不解决布局漂移。

**状态：**

- ✅ 用户已明确确认外壳滚动条消失。
- ✅ 关闭确认框位置恢复正常。

## 3. 关闭确认框“取消”后的 WebView 恢复与竞态问题

**现象风险：**

解决弹窗遮挡后，可能产生新的问题：

- 点击取消后网页不回来。
- 网页回来了，但位置不对。
- 网页尺寸错误。
- 原页签恢复了，但其他页签错位。
- 快速打开弹窗又取消时产生竞态。

**真正难点：**

这不是“显示/隐藏一个 div”，而是一个跨前端和原生层的状态机：

```text
正常显示
→ 暂停网页定位
→ 隐藏原生 WebView
→ 显示确认框
→ 取消
→ 恢复原生 WebView
→ 重新计算位置
→ 恢复正常调度
```

如果执行顺序不正确，可能出现：

```text
刚恢复 WebView
→ 下一次旧的定位任务又把它移走
```

或者：

```text
弹窗已经关闭
→ webviewsSuspended 仍然为 true
→ 后续页签全部不再更新
```

**解决方式：**

- 增加明确的 `closeDialogOpen` 状态。
- 增加 `webviewsSuspended` 状态。
- 弹窗期间停止 BrowserHost 的正常定位调度。
- 取消后恢复原生 WebView。
- 强制执行 `forceGridRelayout`。
- 对“立即取消”和“多页签恢复”增加自动回归检查。

**为什么属于高级模型级：**

这涉及：

- 异步状态机
- Vue 响应式更新
- Tauri IPC 时序
- 原生 WebView 显隐
- 请求动画帧或延迟定位
- 快速用户操作产生的竞态

属于典型的生命周期和并发时序问题。

**状态：**

- ✅ 代码逻辑完成。
- ✅ 自动回归检查通过。
- ⚠️ 用户尚未明确确认“点击取消后网页完整恢复”，因此不应记录成完整 GUI PASS。

## 4. 无边框窗口无法可靠拖动

**现象：**

- 应用采用无边框窗口后，顶部区域无法稳定拖动。
- 有时拖动无响应。
- 有时事件触发多次。
- 重启或换运行方式后表现不一致。

**真正根因：**

一方面，Linux WebKitGTK 不能完全照搬 Chromium/Electron 的：

```css
-webkit-app-region: drag;
```

另一方面，代码中可能存在多个拖动入口：

```text
mousedown
pointerdown
data-tauri-drag-region
手动 startDragging
```

多个入口重叠时，会出现：

- 重复触发
- 事件被子组件截获
- 双击最大化与拖动冲突
- 权限配置不一致

**最终解决方式：**

- 统一成一个原生拖动入口。
- 不依赖 Chromium 专属的 `-webkit-app-region`。
- 保留双击最大化。
- 核对 Tauri 主窗口拖动权限。
- 增加 `check-window-drag.mjs` 防止恢复重复事件路径。
- 接入 `pre-merge`。

**验证：**

```text
node scripts/check-window-drag.mjs
```

通过，并且用户进行了真实桌面拖动验收。

**提交：**

```text
7cb746a fix(M5): make frameless window drag reliable
```

**为什么属于高级模型级：**

需要同时理解：

- WebKitGTK 与 Chromium 的差异
- 浏览器事件传播
- Tauri 原生窗口 API
- 双击与拖动冲突
- Linux 真实桌面行为

单看 Vue 代码很难找出完整根因。

**状态：**

- ✅ 自动检查通过。
- ✅ 用户桌面实测通过。

## 5. 点击应用图标却启动旧 debug 版，出现 `localhost:1421 Connection refused`

**现象：**

- 源码已经修复。
- `.deb` 也重新安装了。
- 点击应用菜单图标后，仍然显示白屏。
- 页面报错：

```text
localhost:1421 Connection refused
```

**真正根因不是一个，而是四个因素叠加：**

### 第一层：错误启动器

用户目录中存在：

```text
~/.local/share/applications/mvp-browser-os.desktop
```

其中：

```text
Exec=/.../src-tauri/target/debug/mvp-browser-os
```

### 第二层：debug 版依赖 Vite

debug 程序期望：

```text
localhost:1421
```

存在开发服务器。

重启电脑后 Vite 没运行，所以白屏。

### 第三层：用户级启动器优先级更高

Linux 桌面环境通常优先读取：

```text
~/.local/share/applications/
```

而不是：

```text
/usr/share/applications/
```

所以重新安装 `.deb` 并不会自动删除同名的用户级旧启动器。

### 第四层：单实例机制

项目用了单实例插件。旧进程没有彻底退出时，新 release 程序可能只会把旧窗口重新聚焦，让人误以为新包没有生效。

**最终解决方式：**

先确定到底运行的是谁：

```bash
ps -eo pid,lstart,args | grep mvp-browser-os
readlink -f /proc/<PID>/exe
```

然后删除旧启动器：

```bash
rm -f ~/.local/share/applications/mvp-browser-os.desktop
```

重新安装正式包：

```bash
sudo apt install --reinstall \
'/home/ainfinit/Documents/极智简单/V3/mvp-browser-os-v3/src-tauri/target/release/bundle/deb/mvp-browser-os_0.1.0_amd64.deb'
```

系统级正式启动器应为：

```text
Exec=mvp-browser-os
```

对应正式程序：

```text
/usr/bin/mvp-browser-os
```

**为什么属于高级模型级：**

这个问题看起来像“前端白屏”，但实际需要区分：

```text
源码
debug 二进制
release 二进制
.deb 包内二进制
/usr/bin 已安装二进制
.desktop 启动入口
当前正在运行的进程
```

普通模型很容易只建议：

```bash
npm run dev
```

这会让白屏暂时消失，却继续错误地使用 debug 启动器。

**状态：**

- ✅ 根因已定位。
- ✅ 修复命令已明确。
- ⚙️ 最新一轮安装包仍在进行安装测试。

## 9. 页签过多时出现顶部横向系统滚动条

**根因：**

页签栏使用：

```css
overflow-x: auto;
```

WebKitGTK 会直接绘制系统横向滚动轨道。

**解决方式：**

保留滚轮和触控板横向滚动能力，但隐藏轨道：

```css
.unified {
  overflow-x: auto;
  overflow-y: hidden;
  scrollbar-width: none;
  -ms-overflow-style: none;
}

.unified::-webkit-scrollbar {
  display: none;
}
```

**关键点：**

不是：

```css
overflow-x: hidden;
```

因为那会让被遮住的页签无法访问。

而是：

```text
保留滚动能力
隐藏滚动条外观
```

**状态：**

- ✅ 代码完成。
- ✅ 回归检查覆盖。
- ⚙️ 最新安装版需要再看一次。

# 三、🟢 常规问题

## 13. 安装 `.deb` 报“命令行中有不支持的文件”

**错误命令：**

```bash
rm -f \~/.local/share/applications/mvp-browser-os.desktop

sudo apt install --reinstall \
'./src-tauri/target/release/bundle/deb/mvp-browser-os\_0.1.0\_amd64.deb'
```

**根因：**

Markdown 转义字符被复制进了 Shell：

```text
\~ 不是 ~
\_ 不是 _
```

尤其是在单引号内部，反斜杠会成为实际文件名的一部分。

**正确命令：**

```bash

# 五、最典型的“高级模型与普通模型差异”

| 问题 | 普通模型容易给出的答案 | 最终正确处理 |
|---|---|---|
| 浮窗被网页遮挡 | 无限提高 `z-index` | 识别原生 WebView 层级，弹窗时隐藏或移开 WebView |
| 纵向滚动条 | 给 `body` 加 `overflow:hidden` | 找到主窗口与子 WebView 物理尺寸同步不一致 |
| 点击图标白屏 | 启动 `npm run dev` | 找到旧 `.desktop` 指向 debug，并处理用户级启动器优先级 |
| 新包不生效 | 再构建一次 | 追踪源码、dist、release、deb、安装文件、运行进程的身份链 |
| 无边框不能拖动 | 使用 `-webkit-app-region:drag` | 针对 WebKitGTK 使用单一原生拖动入口 |
| 关闭确认框可见后网页不恢复 | 简单 `v-if` 切换 | 设计暂停、隐藏、取消、恢复、重布局的状态机 |
| 713/714 不动 | 立即中止重试 | 检查 `rustc` 进程和 CPU，确认正在 LTO 链接 |

当前应记录为：

```

## 2. 保存和删除分支

关闭页签确认框中的：

```text

删除
取消
```

三个分支需要分别实测，不能只因为确认框出现就全部写成 PASS。

## 3. 最新 `.deb` 最终验收

当前正在处理最新安装包安装。必须确认从应用菜单打开的确实是：

```text
/usr/bin/mvp-browser-os
```

而不是旧 debug 程序。

## 4. 最后一次 Git push

最新修复提交后，`git push origin master` 曾遇到 workspace credits 耗尽。代码和本地 commit 不会因此丢失，但远端是否已同步需要检查：

```bash
git status -sb
git log --oneline origin/master..HEAD
```

如果第二条有输出，说明本地仍有提交没有推送。

# 最终结论

当前最有技术价值、最明显需要高级模型能力的，不是 CSS 和安装命令，而是以下五大类：

1. **原生 WebView 与 HTML 浮层的窗口层级冲突。**
2. **主窗口和多个子 WebView 的物理尺寸漂移。**
3. **关闭确认框期间的 WebView 暂停、隐藏和恢复状态机。**
4. **源码、debug、release、DEB、已安装程序和运行进程的身份追踪。**
5. **WebKitGTK 无边框窗口拖动的原生事件与权限处理。**

这些问题的共同特点是：

> 表面症状出现在 Vue/CSS，但真正根因存在于 Rust、Tauri、GTK、WebKitGTK、Linux 桌面入口或运行时生命周期中。普通模型容易“修症状”，高级模型的价值是确定真正的故障层，并把修复固化成回归检查。
