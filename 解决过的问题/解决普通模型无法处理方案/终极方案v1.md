可以完成**大部分**，但不能把整套改造一次性交给普通模型，并期待它自己完成架构判断、原生实现和最终验收。

更准确的分工是：

> **普通模型负责 Vue、业务状态、纯函数、Mock、测试和脚本；高级模型负责 WebView 原生边界、GTK/Tauri 时序与最终架构审查；真实桌面结果由人工验收。**

按当前项目估算：

| 类型 | 占改造工作量 | 适合谁 |
|---|---:|---|
| Vue/UI/业务重构 | 约 45% | 普通模型 |
| 接口、状态机、Mock、测试 | 约 25% | 普通模型，在明确契约下 |
| Rust/Tauri/GTK/WebView 原生部分 | 约 20% | 高级模型 |
| 安装版、窗口层级、拖动等真实验收 | 约 10% | 人工 + 高级模型分析 |

所以，**约 65%～75% 可以交给普通模型**，但前提是先把原生边界和验收契约定清楚。

这些任务不能只说一句“重构一下”，否则普通模型容易改坏。

普通模型可以迁移调用，但任务必须明确：

```text
closeDialogOpen
```

应该如何合并。

```ts
type BrowserMode =
```

普通模型再迁移。

# 三、必须由高级模型处理的部分

## 1. `sync_browser_scene` 的 Rust 原生实现

前端定义场景普通模型可以做，但 Rust 侧如何应用必须由高级模型处理：

```text
先隐藏哪些 WebView
何时移动
何时 resize
何时 show
失败时如何回滚
部分 WebView 不存在怎么办
重复 scene 是否幂等
旧请求晚到怎么办
```

特别需要考虑：

```text
Scene 100 发出
Scene 101 发出
Scene 100 晚于 101 完成
```

如果没有版本号，旧场景可能覆盖新场景。

建议由高级模型设计：

```ts
interface BrowserScene {
  revision: number;
  views: SceneView[];
}
```

Rust 只接受更大的 revision。

---

## 2. GTK/WebKitGTK 的窗口层级

任何涉及：

```text
show
hide
move
resize
reparent
size_allocate
physical size
native layout
```

都属于原生危险区。

普通模型可能写出“语法正确但桌面行为错误”的代码。

---

## 3. 逻辑像素与物理像素转换

这个问题涉及：

- Linux DPI。
- Wayland 缩放。
- X11 缩放。
- GTK scale factor。
- Tauri 逻辑坐标。
- CSS `getBoundingClientRect()`。

必须规定：

```text
前端只传逻辑像素
Rust 只在一个地方转换
任何其他地方不得乘 scaleFactor
```

这一设计和实现需要高级模型。

---

## 4. 自定义无边框窗口

你已明确拒绝恢复系统标题栏，因此下面这些仍属于高级模型区域：

- 原生拖动。
- 双击最大化。
- 拖动与页签点击冲突。
- Wayland/X11 差异。
- Tauri 权限。
- 窗口尺寸修复。
- 原生事件监听。

普通模型可以修改标题、图标和按钮样式，但不应修改拖动机制。

---

## 5. 原生 WebView 销毁与后台行为

关闭页签自动保存不等于简单执行：

```ts
tabs.splice(index, 1);
```

还需要处理：

- WebView 是否仍有下载。
- 音频是否正在播放。
- 页面是否触发离开确认。
- 原生资源是否释放。
- 关闭失败后如何恢复。
- 正在导航时关闭。
- 创建尚未完成时关闭。

这部分应由高级模型定义和实现。

---

## 6. 一页签一 WebView还是固定池

这不是普通编码任务，而是产品架构决策。

需要先回答：

- 后台音频是否必须继续。
- 下载是否必须继续。
- 未保存表单是否要保留。
- 后台登录刷新是否必须继续。
- 100 个页签时内存目标是多少。
- 宫格最多显示多少页。

普通模型不能替你做这个决定。

# 四、必须由人工验收的部分

即使高级模型写完，也不能仅凭自动测试宣告通过。

需要人工检查：

| 场景 | 原因 |
|---|---|
| 确认框或面板是否被网页遮挡 | 属于原生窗口层级 |
| 窗口能否拖动 | 桌面真实行为 |
| 双击能否最大化 | 窗口管理器行为 |
| 横纵滚动条是否异常 | GTK/WebKitGTK 实际渲染 |
| 安装后图标启动哪个程序 | 桌面入口与旧进程 |
| 多显示器/DPI | 物理像素差异 |
| Wayland/X11 | 平台行为不同 |
| 后台音频和下载 | 产品运行行为 |
| 恢复最近关闭页签 | 数据与原生生命周期结合 |

普通模型可以生成验收清单，但不能替代你的实际点击确认。

# 五、不能一次把这段提示词交给普通模型

下面这种任务普通模型很容易失败：

```text

增加错误面板，
删除所有浮层，
```

它涉及：

- 产品决策。
- Vue 重构。
- Rust 原生代码。
- GTK 时序。
- 数据迁移。
- 安装包。
- GUI 验收。

普通模型容易：

- 改动范围失控。
- 同时修改几十个文件。
- 删除仍被原生层依赖的状态。
- 编译通过但桌面行为错误。
- 把未人工验收写成 PASS。

# 七、推荐实际分工

## 高级模型先做一次

让高级模型完成：

1. 定义 `BrowserRuntime` 契约。
2. 定义 `BrowserScene` 契约。
3. 定义自动保存关闭协议。
4. 确定原生层错误码。
5. 标明高级模型专用文件。
6. 写第一版架构边界检查。
7. 给出迁移顺序和每步回滚点。

完成这些后，高级模型不需要一直参与。

## 普通模型连续完成

普通模型随后可以处理：

1. 删除成功提示。
2. 状态栏消息重构。
3. 独立错误面板。
4. `BrowserViewportAnchor`。
5. `MockBrowserRuntime`。
6. 纯布局函数。
7. 关闭状态机。
8. 最近关闭列表。
9. 调用点逐步迁移。
10. 文档和测试。
11. 一键脚本。
12. 清理旧组件。

## 高级模型最后收口

最后再让高级模型：

1. 实现或审核 Rust `sync_browser_scene`。
2. 审核 GTK 生命周期。
3. 检查竞态和逻辑/物理像素。
4. 核对 Tauri 权限。
5. 审核安装包与进程身份。
6. 判断哪些 GUI 项目仍需人工验收。

# 最终判断

| 改造项 | 普通模型能否完成 |
|---|---|
| 成功不弹浮窗 | **可以独立完成** |
| 错误放状态栏 | **可以独立完成** |
| 独立错误面板 Vue UI | **可以，在布局约束下** |
| 删除关闭确认框 | **可以，但要等自动保存稳定后** |
| 自动保存业务逻辑 | **可以，在明确产品规则和接口下** |
| 最近关闭页签 | **可以** |
| 重写 Vue WebView-safe Shell | **可以分阶段完成** |
| BrowserRuntime 接口 | **可以按既定契约实现** |
| MockBrowserRuntime | **可以** |
| 纯布局和状态机 | **可以** |
| 调用点迁移 | **可以逐文件完成** |
| Rust 原生 scene 同步 | **不建议普通模型独立完成** |
| GTK/WebKitGTK 层级与尺寸 | **不建议** |
| 无边框拖动原生实现 | **不建议** |
| WebView 销毁时序与竞态 | **不建议** |
| 最终 Linux GUI 验收 | **必须人工参与** |

结论是：

> **普通模型能完成绝大多数“把项目变简单”的工作，但“先定义简单架构”和“实现底层原生边界”仍然需要高级模型。**

最安全的模式不是“高级模型写所有代码”，而是：

```text
高级模型定边界和契约
→ 普通模型分任务迁移
→ 自动门禁限制越界
→ 高级模型审核原生部分
→ 人工验收桌面行为
```
