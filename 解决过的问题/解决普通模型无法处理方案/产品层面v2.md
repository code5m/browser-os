## 1. Chrome 关闭页签是什么原则？

Chrome 的原则更准确地说是：

> **立即关闭 + 可恢复，而不是关闭前询问“保存、删除、取消”。**

用户关闭页签时，Chrome 通常直接关闭，不弹浏览器自己的三选一确认框；关闭后可以用 `Ctrl+Shift+T` 按关闭顺序恢复最近关闭的页签。Chrome 还可以配置启动时“继续浏览上次打开的页面”。

但是需要特别区分：

### Chrome 保存的不是完整网页状态

Chrome 可以恢复：

- URL
- 页签顺序
- 窗口关系
- 部分导航历史
- Cookie 和登录状态
- 最近关闭记录

Chrome **不保证保存**：

- 网页中尚未提交的表单
- 网页内存中的 JavaScript 状态
- 正在执行的网页任务
- 编辑器里尚未由网站自身保存的内容
- 视频播放到的精确运行现场
- WebSocket 和后台连接状态

现代浏览器的原则是：网页应用应当在进入隐藏状态等可靠时机保存自己的业务数据，不能依赖关闭时的 `unload` 回调，因为页面可能直接被冻结或丢弃。

所以你的项目不应该把功能叫做“保存整个网页”，而应叫：

> **关闭前保存页签会话快照。**

建议你的关闭流程变为：

```text
点击关闭页签
    ↓
保存本项目可控制的会话信息
    ↓
保存成功
    ↓
关闭原生 WebView
    ↓
记录到“最近关闭”
    ↓
不显示成功浮窗
```

保存内容可以包括：

```text
tabId
URL
标题
图标
页签顺序
是否固定
所属分组
当前工作区
宫格位置
最后访问时间
必要的导航历史
```

失败时不能静默丢失：

```text
保存失败
→ 保留页签不关闭
→ 状态栏显示错误
→ 独立错误面板提供详情和重试
```

### 网页自己的未保存提示怎么办？

个别网站可能使用 `beforeunload` 提示“内容尚未保存”。这属于**网页自己的离开确认**，不是你的 Vue 关闭页签三选一弹窗。

产品规则可以是：

- 删除你自己的“保存／删除／取消”确认框。
- 不主动伪造网页保存能力。
- 网页内核自身产生的未保存警告，暂时保留。
- 浏览器会话快照只负责恢复页签，不承诺恢复网页未提交内容。

因此建议采用的准确产品定义是：

> **页签默认立即关闭；系统自动保存可恢复的会话元数据；用户可从最近关闭中恢复。**

## 2. Chrome 是多少个 WebView？

Chrome **没有固定的 1 个、4 个或 10 个 WebView 上限**。

它也不是简单的：

```text
1 个页签 = 1 个固定渲染进程
```

Chrome 使用：

```text
浏览器主进程
+ 多个渲染进程
+ GPU 进程
+ 网络等工具进程
```

在站点隔离机制下：

- 一个页签可能涉及多个渲染进程，例如存在跨站 iframe。
- 多个同站点页面可能复用渲染进程。
- 页签导航到另一个站点时可能切换渲染进程。
- 具体数量由站点、iframe、隔离策略、内存和浏览器调度决定。

Chrome 也不会简单规定“最多只让 4 个页签存在”。它会通过 Memory Saver 等机制让不活跃页签进入停用状态，在用户重新访问时恢复，以降低内存消耗。音视频、下载、部分填写的表单、固定页签等情况可能被保留为活动状态。

### 你的当前项目是多少？

根据本次项目架构，当前更接近：

```text
打开 N 个浏览器页签
≈ 创建 N 个原生子 WebView
```

也就是说目前不是固定 4 个。

我之前提到“最多 4 个”，是一个**简化架构的建议**，不是 Chrome 的标准，也不是你当前项目已经实施的状态。

### 你的项目应该选多少？

可以分成三种路线：

| 路线 | 原生 WebView 数量 | 特点 |
|---|---:|---|
| 当前路线 | 基本等于打开页签数 | 后台状态保持较好，但原生窗口管理复杂 |
| 极简路线 | 普通模式始终 1 个 | 最简单，但切页签时可能需要重新加载 |
| 可见槽位路线 | 等于当前可见宫格数量，通常 1～4 个 | 复杂度与体验比较平衡 |

我更准确的建议不是“永远固定 4 个”，而是：

> **原生 WebView 数量等于当前可见网页数量。**

例如：

```text
普通模式：1 个原生 WebView
双栏模式：2 个原生 WebView
2×2 宫格：4 个原生 WebView
其余后台页签：只保存会话元数据
```

但这会改变后台页签行为。后台网页可能停止：

- 播放音频
- 下载
- 长时间计算
- 登录刷新
- 实时通信
- 未保存表单状态

因此这个决定不能只从技术简单考虑：

- 产品要求接近 Chrome、后台页签必须继续运行：保留“一页签一 WebView”。
- 产品核心是工作区、会话和宫格，不强调所有后台网页持续运行：使用可见槽位模式。

当前不要直接把上限改成 4，应该先确定后台页签是否必须持续运行。

## 6. 错误和状态只在状态栏或独立面板显示

确认采用，但需要明确“独立面板”的定义：

> 独立面板必须占据真实布局空间，不能浮在原生 WebView 上方。

推荐规则：

| 信息类型 | 显示位置 |
|---|---|
| 普通加载状态 | 状态栏 |
| 非阻断错误 | 状态栏 |
| 操作失败 | 状态栏，并提供“查看详情” |
| 长错误详情 | 右侧或底部独立面板 |
| 日志和诊断 | 独立诊断面板 |
| 会话管理 | 独立页面或侧边面板 |
| 危险删除 | 独立页面中的确认区域，或原生对话框 |

右侧面板打开时应该是：

```text
主布局总宽度
├── WebView 区域缩窄
└── 错误面板占据固定宽度
```

然后重新同步原生 WebView 的矩形。

不应该是：

```text
错误面板 position: fixed
z-index: 99999
直接覆盖 WebView
```

全屏独立页面则应该：

```text
先隐藏原生 WebView
→ 再显示完整 Vue 页面
```

这样不会再次制造浮层遮挡问题。

## 7. 目前是 Vue 框架吗？能否重新编写时考虑 WebView？

### 当前确实是 Vue 前端

根据这次项目中已经出现的文件：

```text
src/App.vue
src/components/layout/UnifiedTabBar.vue
src/components/layout/MainArea.vue
src/components/layout/StatusBar.vue
src/components/browser/BrowserHost.vue
src/components/browser/SessionCloseDialog.vue

src/stores/useBrowserStore.ts
src/stores/useLayoutStore.ts
src/stores/useSessionStore.ts
src/composables/useBrowserHost.ts
```

可以确认前端是 Vue 单文件组件和 TypeScript 状态逻辑。

整体结构是：

```text
Vue 前端外壳
+ Tauri/Rust
+ Linux 原生子 WebView
+ 自研 browser-tabs 插件
```

构建日志也确认主程序实际链接了 Tauri 和自研 `tauri_plugin_browser_tabs`。

### 可以重新设计，但不是“重写 Vue 框架本身”

Vue 本身没有问题。真正需要重写的是：

> **Vue 应用外壳和 WebView 集成架构。**

无论使用 Vue、React 还是其他框架，都不能仅靠 CSS 让 HTML 压过一个 Linux 原生子 WebView。

因此正确方向不是：

```text
换掉 Vue
```

而是：

```text
保留 Vue
重新设计一个 WebView-aware Vue Shell
```

## 推荐的新 Vue 结构

```text
App.vue
└── WebViewSafeShell.vue
    ├── CustomTitleBar.vue
    ├── UnifiedTabBar.vue
    ├── WorkspaceLayout.vue
    │   ├── LeftPanel.vue
    │   ├── BrowserViewportAnchor.vue
    │   └── RightPanel.vue
    └── StatusBar.vue
```

### `BrowserViewportAnchor.vue`

这个组件只负责：

- 在 Vue 布局里保留一块空白区域。
- 使用 `ResizeObserver` 获取它的坐标和尺寸。
- 将最终矩形同步给原生 WebView。
- 自己不承载网页。
- 不允许子组件覆盖它。

可以理解为：

```text
Vue 负责画一个“网页应该放在这里”的空框
Rust/GTK 负责把原生 WebView 放进这个空框
```

### 关键规则一：WebView 区域是禁浮层区

```text
BrowserViewportAnchor 内：
- 禁止 Modal
- 禁止 Toast
- 禁止 Popover
- 禁止 Dropdown
- 禁止 position: fixed
- 禁止 Teleport 浮层覆盖
```

### 关键规则二：面板必须改变布局

打开右侧错误面板时：

```text
原来：
[ WebView 1200px ]

打开面板：
[ WebView 850px ][ 错误面板 350px ]
```

Vue 重新计算 `BrowserViewportAnchor`，再通知 Rust 缩小 WebView。

这样错误面板不是覆盖网页，而是和网页并列。

### 关键规则三：全屏 Vue 页面必须先隐藏 WebView

例如进入：

- 会话管理
- 设置
- 数据库管理
- 错误诊断
- 帮助页面

流程应为：

```text
切换到应用页面
→ Rust 隐藏所有原生 WebView
→ Vue 显示完整页面

返回浏览器
→ Vue 计算网页区域
→ Rust 恢复对应 WebView
```

### 关键规则四：只有一个文件能调用 Tauri

建议增加：

```text
src/platform/browser-runtime/BrowserRuntime.ts
src/platform/browser-runtime/TauriBrowserRuntime.ts
```

只有 `TauriBrowserRuntime.ts` 可以调用：

```ts
invoke(...)
```

Vue 组件和 Store 不直接操作原生 WebView。

组件只表达：

```ts
browserController.openTab()
browserController.closeTab()
browserController.changeLayout()
browserController.openErrorPanel()
```

### 关键规则五：一次同步完整场景

不要再由多个组件分别执行：

```text
hide
move
resize
show
resume
```

改为一次发送：

```ts
interface BrowserScene {
  views: Array<{
    tabId: string;
    visible: boolean;
    rect: {
      x: number;
      y: number;
      width: number;
      height: number;
    };
  }>;
}
```

Vue 计算最终结果：

```ts
await browserRuntime.syncScene(scene);
```

Rust 按固定顺序统一处理所有原生 WebView。

这能显著减少：

- 关闭页签竞态
- WebView 错位
- 弹窗恢复失败
- 横纵滚动条漂移
- 多处重复调用 Tauri

# 推荐的改造顺序

不要一次性推倒全部 Vue 代码，按下面顺序风险最低。

### 第一阶段：关闭页签自动保存

```text
新增会话快照保存
新增最近关闭记录
保存成功后关闭
保存失败则不关闭
删除 SessionCloseDialog
删除弹窗期间隐藏／恢复 WebView 的复杂状态
```

这是当前收益最高的一步。

### 第二阶段：建立 WebView 安全壳

新增：

```text
WebViewSafeShell.vue
BrowserViewportAnchor.vue
PanelHost.vue
```

明确网页区域不能被 HTML 浮层覆盖。

### 第三阶段：统一原生调用

新增：

```text
BrowserRuntime
TauriBrowserRuntime
syncScene
```

把散落在 `App.vue`、Store、Composable 中的原生调用收拢。

### 第四阶段：迁移状态栏和独立面板

- 成功信息全部静默。
- 错误进入状态栏。
- 长错误进入独立布局面板。
- 设置和会话管理改成独立页面。
- 清理所有覆盖网页的 HTML 浮层。

### 第五阶段：再决定 WebView 数量

先不要立即改成固定 4 个。

需要先确认这些产品要求：

```text
后台页签是否必须播放音频
后台下载是否必须继续
网页登录状态是否必须原地保留
未提交表单是否必须保留
后台网页任务是否必须继续
```

确认后再选择：

```text
一页签一 WebView
或
可见区域 WebView 池
```
