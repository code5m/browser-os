可以。核心不是让普通模型学会 GTK、WebKitGTK 和 Tauri，而是把这些复杂技术**封进一个稳定的小核心**，让普通模型只修改 Vue、业务状态和纯函数。

你的目标应该是：

> **普通模型处理 80% 的 UI、业务和测试；高级模型只维护 20% 的 Linux 原生适配层。**

不是把整个项目都降级成简单代码，而是明确划分“安全区”和“原生危险区”。

# 一、先从产品层面减复杂度

有些复杂度不是代码写得差，而是产品功能天然复杂。下面几个调整最有效。

## 1. 减少同时存在的原生 WebView 数量

当前复杂度最大的来源是：

```text
一个页签
=
一个 Linux 原生子 WebView
```

页签越多，越容易出现：

- WebView 遮挡 HTML 弹窗
- 主窗口和子窗口尺寸漂移
- 切换、隐藏、恢复竞态
- 多页签关闭顺序问题
- GTK 原生窗口层级问题

建议按产品需求选择：

### 最简单方案：只保留一个活动 WebView

```text
页签列表只保存：
URL
标题
图标
会话信息

只有当前页签真正对应一个原生 WebView
```

切换页签时，把当前 WebView 导航到目标地址或恢复会话。

优点是几乎消灭：

- 多 WebView 层级问题
- 多窗口定位问题
- 多 WebView 恢复问题

缺点是后台网页不会继续保持完整运行状态。

### 平衡方案：固定 WebView 池

假如宫格模式是核心功能，可以固定：

```text
最多 4 个原生 WebView
```

而不是一个页签一个 WebView。

例如：

```text
普通模式：使用 1 个槽位
2×2 宫格：使用 4 个槽位
其余页签：只保存元数据
```

这样不论有 10 个还是 100 个页签，原生子窗口最多只有 4 个。

这是最适合你当前项目的平衡方案。

---

## 2. 去掉“关闭页签三选一确认框”

现在关闭页签涉及：

```text
保存
删除
取消
```

这带来了：

- HTML 确认框
- WebView 暂停
- WebView 隐藏
- 取消恢复
- 保存和删除分支
- 异步竞态
- 原生层级遮挡

更简单的产品设计是：

```text
关闭页签
→ 自动保存会话
→ 立即关闭
```

删除会话放到单独的“会话管理”页面。

还可以提供：

```text
最近关闭的页签
撤销关闭
```

这样就不再需要关闭确认框，也直接消灭了本次最复杂的浮窗问题。

推荐行为：

```text
关闭页签：自动保存
彻底删除：在会话管理中执行
误关闭：最近关闭中恢复
```

---

## 3. 考虑恢复系统原生标题栏

当前无边框窗口带来了：

- 自定义拖动
- 双击最大化
- Tauri 权限
- WebKitGTK 事件差异
- 拖动区域冲突
- Linux 桌面兼容问题

如果产品外观不是必须完全自定义，可以恢复系统标题栏：

```text
decorations: true
```

那么系统自动处理：

- 拖动
- 最大化
- 最小化
- 关闭
- Wayland/X11 兼容
- 双击标题栏

这可以直接删除一整类需要高级模型处理的问题。

如果必须保留无边框窗口，则要把拖动功能完全封装到一个模块，普通模型不得碰。

---

## 4. 不允许 HTML 浮层覆盖网页区域

制定一个永久规则：

```text
网页区域内禁止 HTML Toast、Popover、Dropdown、Modal。
```

可以采用：

- 普通提示只显示在状态栏。
- 错误信息显示在独立面板。
- 必须确认的操作使用统一 ModalCoordinator。
- 不允许任何组件自行写 `position: fixed` 覆盖网页。

这样普通模型就不用理解原生 WebView 层级。

# 三、只允许一个地方调用 Tauri

目前最容易产生复杂度的情况是：

```text
App.vue 调一次 invoke
Store 调一次 invoke
Composable 又调一次 invoke
组件直接控制 WebView
Rust 还有自己的定时校正
```

普通模型看到这种结构，很难判断谁才是真正控制者。

应该规定：

> 整个前端只有 `TauriBrowserRuntime.ts` 可以调用 Tauri API。

例如：

```ts
export interface BrowserRuntime {
  syncScene(scene: BrowserScene): Promise<void>;
  createTab(tab: NativeTabSpec): Promise<void>;
  destroyTab(tabId: string): Promise<void>;
  navigate(tabId: string, url: string): Promise<void>;
}
```

具体实现：

```ts
import { invoke } from "@tauri-apps/api/core";

export class TauriBrowserRuntime implements BrowserRuntime {
  async syncScene(scene: BrowserScene): Promise<void> {
    await invoke("sync_browser_scene", { scene });
  }

  async createTab(tab: NativeTabSpec): Promise<void> {
    await invoke("create_browser_tab", { tab });
  }

  async destroyTab(tabId: string): Promise<void> {
    await invoke("destroy_browser_tab", { tabId });
  }

  async navigate(tabId: string, url: string): Promise<void> {
    await invoke("navigate_browser_tab", { tabId, url });
  }
}
```

然后禁止：

```text
App.vue
components/**
stores/**
composables/**
```

直接导入：

```ts
@tauri-apps/api
```

这样普通模型处理 UI 时，不会意外破坏原生层。

# 四、从“命令式控制”改成“声明式场景同步”

当前容易发生竞态的方式是：

```text
hide
move
resize
show
hide other views
resume
relayout
```

这些操作中间任何一步失败，窗口就会处于半完成状态。

建议改成一个命令：

```text
sync_browser_scene
```

前端一次性描述最终想要的结果：

```ts
export interface BrowserScene {
  suspended: boolean;
  views: Array<{
    tabId: string;
    visible: boolean;
    x: number;
    y: number;
    width: number;
    height: number;
  }>;
}
```

例如关闭确认框打开时：

```ts
const scene: BrowserScene = {
  suspended: true,
  views: tabs.map(tab => ({
    tabId: tab.id,
    visible: false,
    x: 0,
    y: 0,
    width: 0,
    height: 0,
  })),
};
```

确认框取消后：

```ts
const scene = createVisibleScene(currentLayout);
await runtime.syncScene(scene);
```

Rust 侧统一应用：

```text
验证所有参数
→ 计算原生坐标
→ 隐藏不应显示的 WebView
→ 移动和缩放可见 WebView
→ 最后统一显示
```

普通模型只需要理解：

```text
当前状态
→ 应该生成什么 BrowserScene
```

不用理解 GTK 操作顺序。

# 五、布局必须变成纯函数

当前布局问题会变复杂，是因为以下内容可能混在一起：

- DOM 测量
- Store 状态
- WebView 移动
- CSS 像素
- 物理像素
- GTK 尺寸校正

应拆成两步。

## 第一步：纯布局计算

```ts
type Rect = {
  x: number;
  y: number;
  width: number;
  height: number;
};

export function computeBrowserLayout(
  viewport: Rect,
  tabIds: string[],
  mode: "single" | "grid",
): Record<string, Rect> {
  // 这里只计算，不调用 Tauri，不操作 DOM
}
```

它只接收数据，返回数据。

可以直接测试：

```ts
expect(
  computeBrowserLayout(
    { x: 0, y: 64, width: 1200, height: 736 },
    ["a"],
    "single",
  ),
).toEqual({
  a: { x: 0, y: 64, width: 1200, height: 736 },
});
```

## 第二步：原生层应用布局

```ts
const layout = computeBrowserLayout(viewport, visibleTabIds, mode);
await runtime.syncScene(toBrowserScene(layout));
```

坐标转换只允许发生一次：

```text
Vue 统一使用 CSS 逻辑像素
Rust Linux adapter 统一转换为物理像素
```

禁止其他地方自行乘缩放比例。

# 六、用显式状态机代替多个布尔值

像下面这种状态很容易让普通模型出错：

```ts
closeDialogOpen
webviewsSuspended
isRestoring
isClosing
pendingTabId
```

因为可能出现非法组合：

```text
closeDialogOpen = false
webviewsSuspended = true
```

应该改成一个联合状态：

```ts
type CloseFlow =
  | { state: "idle" }
  | { state: "confirming"; tabId: string }
  | { state: "saving"; tabId: string }
  | { state: "deleting"; tabId: string }
  | { state: "restoring"; tabId: string };
```

所有转换集中在一个 reducer：

```ts
type CloseAction =
  | { type: "REQUEST_CLOSE"; tabId: string }
  | { type: "CONFIRM_SAVE" }
  | { type: "CONFIRM_DELETE" }
  | { type: "CANCEL" }
  | { type: "RESTORED" }
  | { type: "COMPLETED" };
```

这样普通模型能清楚看到：

```text
idle
→ confirming
→ saving / deleting / restoring
→ idle
```

不会在多个 Store、组件和 Composable 中同时修改状态。

如果采用“关闭自动保存”，这个状态机还可以进一步简化成：

```text
idle
→ closing
→ idle
```

# 七、给普通模型一个假的 WebView 环境

普通模型最难处理的是：

```text
不运行真实 Linux GTK 环境，就看不到问题
```

所以需要一个：

```text
MockBrowserRuntime
```

例如：

```ts
export class MockBrowserRuntime implements BrowserRuntime {
  public scenes: BrowserScene[] = [];

  async syncScene(scene: BrowserScene): Promise<void> {
    this.scenes.push(structuredClone(scene));
  }

  async createTab(): Promise<void> {}
  async destroyTab(): Promise<void> {}
  async navigate(): Promise<void> {}
}
```

前端开发时可以通过环境变量启用：

```text
VITE_BROWSER_RUNTIME=mock
```

Mock 模式把原生 WebView 显示成普通 HTML 方块：

```text
WebView A
x=0 y=64
1200×736
visible=true
```

这样普通模型可以处理：

- 页签状态
- 宫格布局
- 关闭流程
- 页面尺寸
- UI 样式

而不需要每次打 `.deb`。

真实 GTK 测试只留给最终集成阶段。

# 八、明确每个文件唯一职责

建议给现有文件设置严格边界：

| 文件 | 只允许负责 |
|---|---|
| `App.vue` | 组装页面，不写原生逻辑 |
| `UnifiedTabBar.vue` | 页签显示和用户事件 |
| `SessionCloseDialog.vue` | 展示状态和发送选择 |
| `StatusBar.vue` | 状态文字，不控制 WebView |
| `useBrowserStore.ts` | 浏览器领域状态 |
| `useBrowserHost.ts` | 测量 viewport，不操作业务状态 |
| `browserController.ts` | 协调业务状态与 runtime |
| `TauriBrowserRuntime.ts` | 前端唯一 Tauri 入口 |
| `bridge.rs` | 参数验证和调用 service |
| `linux.rs` | GTK/WebKitGTK 原生操作 |
| `layout.ts` | 纯布局计算 |
| `closeMachine.ts` | 关闭流程状态机 |

一个简单判断规则：

```text
组件不碰 Tauri
Store 不碰 GTK
Rust 不决定业务规则
Linux adapter 不保存业务状态
```

```text
src/stores/**
```

- 文档

```text
src-tauri/src/browser/linux.rs
```

# 十、建立架构边界自动检查

```text
components 不得导入 @tauri-apps/api
stores 不得导入具体 Tauri adapter
```

```js
import assert from "node:assert/strict";
import { readFileSync } from "node:fs";

for (const file of globSync("src/components/**/*.{ts,vue}")) {
```

加入：

```bash
scripts/pre-merge.sh
```

普通模型即使做错，也会立即得到明确错误。

# 十一、把运行环境判断变成一个命令

之前旧 debug、新 release、旧 `.deb`、用户级 `.desktop` 混在一起，非常依赖高级模型推理。

应该建立：

```bash
./scripts/doctor.sh
```

固定输出：

```text
GIT_COMMIT=...
WORKTREE_CLEAN=true
SOURCE_VERSION=...
DEB_BUILD_TIME=...
DEB_SHA256=...
INSTALLED_BINARY=/usr/bin/mvp-browser-os
INSTALLED_SHA256=...
RUNNING_PID=...
RUNNING_EXE=...
DESKTOP_USER_EXEC=...
DESKTOP_SYSTEM_EXEC=...
DEV_SERVER_1421=DOWN
RESULT=PASS
```

普通模型看到输出就能判断：

```text
运行的是 debug 还是 release
安装包是不是最新
桌面入口指向哪里
旧进程是否存在
```

不需要每次重新拼十条 Linux 命令。

# 十二、区分开发版和正式版身份

当前 debug 和 release 使用同一个应用名称，容易产生：

- 同名 `.desktop`
- 同一个单实例 ID
- 旧窗口被重新聚焦
- 开发版覆盖正式版认知

建议开发版使用不同身份：

```text
正式版：
名称：极智简单浏览器OS
identifier：com.jizhijiandan.mvp

开发版：
名称：极智简单浏览器OS Dev
identifier：com.jizhijiandan.mvp.dev
```

图标也可以加 `DEV` 标识。

这样：

```text
开发版不会覆盖正式版
正式版不会连接 localhost
单实例不会互相干扰
应用菜单不会混淆
```

这比反复删除用户级 `.desktop` 更根治。

# 十三、构建、安装、诊断全部一键化

不要让普通模型记住复杂命令。

建议在 `package.json` 统一：

```json
{
  "scripts": {
    "check": "bash scripts/pre-merge.sh",
    "doctor": "bash scripts/doctor.sh",
    "package:deb": "bash scripts/package-deb.sh",
    "install:deb": "bash scripts/install-deb.sh",
    "verify:installed": "bash scripts/verify-installed.sh"
  }
}
```

以后只需要：

```bash
npm run check
npm run package:deb
npm run install:deb
npm run verify:installed
```

其中 `install-deb.sh` 自动完成：

```text
关闭旧实例
删除错误用户级启动器
确认 DEB 存在
输出 SHA-256
执行 apt --reinstall
刷新 desktop database
检查 /usr/bin 二进制
启动正式版
验证运行路径
```

普通模型只需要根据最后的：

```text
RESULT=PASS
```

判断结果。

# 十五、让测试验证行为，而不只是匹配代码字符串

你当前的一些 `.mjs` 检查很有价值，但如果只是：

```js
assert.match(source, /overflow-y:\s*hidden/);
```

它只能证明代码里存在某个字符串，不能证明行为正确。

应该逐步补充三层测试：

## 第一层：纯函数测试

验证：

- 布局坐标
- 关闭状态机
- 页签切换
- 宫格分配
- 取消恢复

普通模型最擅长处理这一层。

## 第二层：Runtime 合约测试

验证：

```text
confirming 状态
→ scene.suspended=true
→ 所有原生 view 不可见

cancel
→ scene.suspended=false
→ 原 tab 恢复可见
```

通过 MockRuntime 完成。

## 第三层：少量真实桌面测试

只保留：

- 窗口拖动
- 原生 WebView 层级
- 安装版入口
- Wayland/X11
- 实际关闭恢复

真实桌面测试不是每个普通模型任务都需要运行。

# 十六、任务本身也要变简单

不要再给普通模型这样的任务：

```text
继续完成验收并安排工作，顺便解决弹窗、滚动条和打包问题
```

这句话同时包含：

- 找 Bug
- 改前端
- 改 Rust
- 打包
- 安装
- GUI 验收
- 写文档
- Git 提交

普通模型很容易越界。

应该拆成任务卡：

```text
任务：删除新建页签成功提示

允许修改：
- src/stores/useLayoutStore.ts
- src/components/layout/StatusBar.vue
- 对应测试

禁止修改：
- src-tauri/**
- tauri-browser-tabs/**
- 窗口布局逻辑

不变量：
- 错误提示仍然保留
- 页签创建行为不能改变

验收命令：
npm run test:ui
npm run check

停止条件：
如果需要修改原生 WebView，请停止并报告。
```

普通模型处理这种任务会稳定很多。

# 十七、推荐的实际改造顺序

## 第一阶段：先解决“看不清运行的是谁”

优先完成：

1. `scripts/doctor.sh`
2. 开发版和正式版不同 identifier
3. 应用显示 commit/build time
4. 一键 package/install/verify
5. 正式提升版本号

这一步几乎不改核心业务，但马上降低排错难度。

# 十八、最推荐你的最终形态

结合你当前浏览器 OS 项目，我建议选择这个方案：

```text
主界面：Vue
业务状态：纯 TypeScript reducer
页签：无限元数据
原生 WebView：固定池，最多 4 个
普通模式：只使用 1 个
宫格模式：最多使用 4 个
关闭页签：自动保存
删除会话：在会话管理中完成
提示：只在状态栏
布局：纯函数计算
原生控制：单一 syncScene
开发版和正式版：完全不同身份
```

这个方案能保留：

- 多页签
- 宫格
- 会话
- 原生网页
- Tauri 的轻量优势

同时大幅减少：

- 原生窗口数量
- 浮窗遮挡
- 关闭状态机
- 多 WebView 恢复
- 尺寸漂移
- debug/release 混淆

# 判断是否改造成功的标准

改造完成后，普通模型收到一个常规需求时，应该满足：

```text
只需要阅读 3～5 个文件
通常只修改 1～3 个文件
不需要理解 GTK
不需要查看 /proc
不需要手动比较 DEB 时间
不直接调用 Tauri invoke
有唯一复现命令
有唯一验收命令
失败时有明确错误信息
```

真正需要高级模型处理的区域只剩：

```text
tauri-browser-tabs/**
Linux GTK/WebKitGTK adapter
Tauri 权限与原生窗口
新的平台适配
原生崩溃和窗口系统问题
```

最优先做的不是大规模重写，而是这四项：

```text
1. BrowserRuntime 接口
2. MockBrowserRuntime
3. syncScene 声明式同步
4. doctor/package/install 一键脚本
```

这四项完成后，普通模型处理项目的成功率就会明显提高。
